# 给 DS：R2 解阻路线，停止逐表语言迁移

日期：2026-10-20。参考已提交版本 `5117448899a6a3cb87301630fe7f83c3dcc4c105`，以及 t30/t31/t34/t35 未提交实验报告。用户目标仍为1s完整记录实用，不以中间表数量作为完成目标。

## 1. 路线决定

**B仅作为当前成果的检查点；下一步采用C路线：原生执行事实 + NumPy批量派生查询索引。**

不要求61张派生表全部以C++生成，也不要求与Python参考的内部ID/排列逐数组相同。保留格式契约、事件/调用/周期/未知语义、查询结果及完整性能验收。

允许Python参与不等于允许重新逐指令处理：旧 `build_tables()` 的逐RUN/逐指令扫描、Python CallTracker重放、读取现成参考表再挂载，都不能作为新输入快路径。

此路线是待验证的工程方案，不是已经测速通过的实现。先完成下面C1/C2的小型原型，依据真实分项计时决定继续或迁移具体热点。

## 2. 依据与当前误区

- t34/t35主要报告“剩余项未实现、上下文内未完成”，不是完整原生实现已被测试证明不可行。
- 61张表是现有Python查询索引的内部布局，不是OpenCSD或用户功能的外部要求。大部分是少数执行事实的派生视图，不是61个独立状态机。
- t31的7张cell表与参考相同，其中6张本来是零占位。7/7一致不能作为真实cell聚合完成的标志，也不值得围绕占位表继续拆任务。
- 6.77s那次阶段数据为read/assemble约3.73s、queryIndex约2.55s、write约0.42s。不是“因为剩余45张表太多而必然无解”。当前native index又解码已写sequence，重复了原始解码循环已经知道的事实，应减少二次遍历。
- 4s是R2阶段预算，完整1s≤10s仍是最终目标。未达阶段预算可以提交正确的中间实现并继续优化，不必每轮停在“失败/枚举缺口”；也不能因此宣布最终达标。

## 3. C1：C++批量输出最小执行事实

沿用已经正确的原生blocks/analysis/anchor/PC/line实现。在原生处理/flush已解析区间时顺便产生数值事实，避免Python重新读sequence推导状态。

建议逻辑字段（不是必须按每指令一个结构体永久保存）：

| 事实 | 推荐表示 |
|---|---|
| 指令身份 | static_id，引用已有唯一PC静态字典 |
| 执行顺序 | instruction ordinal；逻辑seq由事件位置映射，或按块提供起点 |
| 执行状态 | executed/not-taken/unknown，保留区间内部谓词未知 |
| 调用路径 | path_id的变化区间；共享(parent_id,label_id)节点表 |
| 周期 | 稀疏anchor：归属ordinal/seq、uint64周期、cycleSpan |
| 调用与异常 | 事件seq/type/flags/payload、必要前驱与下一函数关系 |
| 解码定位 | 本地block/recordOffset/runSkip，按真实原生布局生成 |

路径在原生状态机改变时编号，Python只消费结果；不得再调用一次Python tracker重建路径。沿用已有静态字典，函数、文件、行、hotspot映射等唯一数据一次准备。

按有界数值批次交给下游，避免逐指令JSON/IPC。可以先用临时二进制或mmap证明接口，随后再融合管道；临时量、RSS和写入时间均计入。周期可以稀疏、路径可以区间化，不要永久新增一份20M条重复字符串/大对象记录。

先以真实10ms/200ms验证事实流，覆盖异常、未知、周期折叠与跨RUN/cell。修复已审查的32位累计周期溢出后再扩大规模。该阶段不用一次交出全部61表。

## 4. C2：NumPy计算派生索引，先做可验证小原型

现有QueryIndex读侧已经有正确性/性能证据，优先复用。Python仅对数值批次/静态集合/单元格执行组装，重活交给NumPy的原生操作。

建议按语义依赖实现：

1. static_id → function/hotspot/flow等映射，唯一静态项处理一次。
2. 执行状态、周期稀疏表、事件字段直接采用C++事实，避免重新解释协议。
3. 函数/路径连续区间用相邻ID变化求边界；跨批次携带最后一个区间。
4. 按cell和hotspot/path ID批量归约count/unknown/first/cycles；完整cell复用，边界保留精确定位。
5. node父子关系来自原生path字典；inclusive/self按明确的祖先关系归约，递归同名帧不能被去重。
6. 生成原查询器需要的数组和meta，使用现有v2编码；默认视图用现有QueryIndex算法生成。

要求：不出现与20M指令同量级的Python对象创建、属性查找、函数调用或for循环。允许按有界批次/cell/唯一节点循环，但需profile确认成本。周期采用整数归约，不用浮点weights丢失大整数精度；明确溢出处理。

**第一个原型只验证static/hotspot映射 + 一个cell的计数/未知/周期 + 跨cell边界。** 对照通过后扩到全部cell，测实际耗时和内存，再继续函数/路径和默认视图。不要再次把“全部45表同时交付”作为单个任务的完成条件。

若NumPy原型仍有明显热点，只把profile证明昂贵的归约放入C++，不预先要求所有表迁移。兼容表可暂时保留零占位，但必须标明用途，不把填零当作完成聚合。

## 5. C3：完成新输入闭环，再做完整验收

先打通：新native.bin → 原生core/事实流 → 批量索引 → 默认视图 → manifest → 现有查询/网页。

没有完整查询信息时，不能把记录发布为“完整快速浏览就绪”。中间结果用实验命令和明确能力字段表达，正常API不得虚报。参考表只能用于比较，不得作为待处理输入的预置索引。

对照优先级：逻辑事件、quality/analysis、default与随机窗口、timeline、首末页和导航。同一语义的ID变化可规范化比较；不是要求任意内部数组字节相同。

阶段证据至少包含：真实200ms、boundary、ETMv3/4小样本；规模输入多段位置及末端对照；同一输入交错多轮，不带profiler的墙钟。合成规模不作为连续真机1s证明。

## 6. 性能与范围纪律

- 每轮拆出core、事实输出、派生索引、默认视图、压缩/校验、发布、首开、物理前端，不用一个总时间猜原因。
- 刚完成正确闭环时即使为6～8s，也先保存真实结果；这不是放宽最终目标。随后依据profile优化重复扫描、写入、压缩和归约。
- R2全部输出/校验/发布和输入准备都要计时。临时文件和内存传递不能从计时边界消失，索引构建不能挪到用户开始浏览之后再冒充完整首屏。
- 现有物理前端规模输入约8.35s，仍需R3优化；R2达到4s也不自动意味着完整链路≤10s。
- Python旧build_tables如果仍需几十/上百秒，不能作为“受控Python索引”最终交付。受控指批量数值计算，须有实测和结构性profile。
- 原版全原生路线保留为后续热点优化选项，本轮先完成可用且可测的混合闭环。
