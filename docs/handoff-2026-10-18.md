## 3. H743 复位入口（重要，且有一条待验证）

### 3.1 三次假说 → 真因

1. ❌"先装断点再复位" → 复位会**清空 FPB 比较器**（实测 `comp[0] 0x88000b51 → 0`），H7 上永远停不到起点
2. ❌"转换成普通 halt 再放行" → 仍失败
3. ✅**真因（对照 web-serial-rtt-tools 的 `#dbg` 页 `_resetCore`）**：H743 的软复位会把
   **调试端口本身**也复位。复位后不重建 SWD，写 `DHCSR` 会"看着成功"（回读 running），
   但核其实不执行 —— 症状是 `PC` 与 `g_trace.loops` 一动不动、无 fault、15 s 后误报"未命中起点"。

### 3.2 修好的序列（`etm/web/app/target.js` 的 `reset()`）

```
DEMCR.VC_CORERESET=1
→ DHCSR = DBGKEY|C_DEBUGEN|C_HALT
→ AIRCR = 0x05FA0004
→ 等 S_HALT（停在 Reset_Handler，实测 0x080063f8）
→ probe.recoverDebugPort()   ← 关键：重建 DP/AP
→ halt()
→ 装业务比较器 + FP_CTRL=KEY|ENABLE
→ 清 VC_CORERESET
→ 放行 = DHCSR 0xA05F0001（回读校验，最多重写 6 次）
→ 200 ms 内没停到起点就做"核真的在跑吗"自检（停→读 PC→放行→再停→再读）
```

**自 2026-10-18 又加了两层兜底**（同一提交内，代码在 `reset()`）：

1. **失败自动重试一次**：任一步失败（尤其"未命中起点"/"核没执行"）→ 先 `recoverDebugPort()`
   重建调试口 → 整段重放一次；仍失败才把错误抛出，且文案前缀变成
   `复位重试后仍失败：…`（`info.resetAttempts` 会记录实际用了几次）。
2. **"核真的在跑吗"自检**：放行后先给 200 ms 正常命中窗口；若没停在起点，就
   "停→读 PC→放行 150 ms→再停→再读"——
   - **PC 没变** → 抛 `放行后核没有执行（…调试端口可能需要重建）`（这才是本次的真因，能直接触发重试）
   - **PC 变了** → 只是还没到起点，继续等到超时（说明是地址/条件问题，不是链路问题）

   有了这条，今天那种"DHCSR 说在跑、实际一动不动"的现场能立刻被指名，而不是笼统报"未命中起点"。

### 3.3 待验证

## 6. 硬坑清单（接手必读）

1. **LA socket 单客户端**：采集进行中再开一个 `Vis()` 会把正在跑的那条连接踢断（`WinError 10053`）。
   要查状态就等它跑完。
2. **采集中不能导出**（`export-data` → NAK `sampling in progress`）；`stop` 会清空缓冲。
3. **1 s 全量导出会卡死**（KingstVIS 无响应，几分钟后才缓过来）；只能 `--time-span` 分片导。
4. **烧录前必须放掉浏览器对探针的占用**（hid 库独占），烧完探针重枚举、桥配置回默认。
5. **H743 复位会清空 FPB 比较器**、且**软复位会重置调试端口**（§3）。
6. **`slice-record.py` 的 `--count N`** 用来只解前 N 片（0.6 s = 3 片），省时间。
7. **页面的「NRST 开漏」复选框**：未连接探针时显示**未知（横杠）**，连上 HID 侧探针后按
   `HID 0x3A` 的真实值刷新；它走 **HID 通道**，ETM 标签占的是 WebUSB 通道，两者不互通。
8. **`etm/web/**` 改动要同步**：`sync-etm-runtime.py` + `sync-etm-page.mjs`，否则 8878 还是旧代码。
   页面默认在 localhost 走 **source**（非 bundle），所以改源码即生效（重载页面即可）。
9. **`_decode_job` 对长窗记录会拒绝按单窗重解**（会只剩第一片），这是有意为之。
