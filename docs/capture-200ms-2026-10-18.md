# 单次采集 / 解码 / 页面显示上限 200 ms（2026-10-18 决策与真机验收）

> **结论**：200 ms 上限在真机生效——0.2 s / 500 MSa/s 记录 `capture-de9b8e0ed24c41c68e5b374f3cb3c9c5`
> 解码完成（packetIssues=0、365,449 B 全消费、3,675,477 指令、浏览索引可读）；此前失败定因为
> **TRACECLK 2 ns 毛刺导致的 nibble 位移**，属"信号质量 + 滤波前置条件"，不是 200 ms 上限或解码器的
> 能力限制。**滤波阈值口径（2026-10-18 包地复测后修正，见 §6）：0 ns 不行；≥2 ns 可行（2 ns 与 4 ns
> 解出的 ETM 流逐字节相同）；4 ns 是已验证的安全边际**（包地前的脏会话里 2 ns 仍失败、4 ns 通过），
> 页面默认保持 **4 ns**；本次为 1 次采集，重复性仍待验证。

## 1. 决策

- **上限**：单次采集、单次解码、页面显示统一 **200 ms**（500 MSa/s 下 **1 亿样本**，≈478 MB CSV）。
  页面 `#duration` 的 `max` 就是 200，`/api/capture` 对 >200 ms、rate>500 MSa/s 或
  `rate × seconds > 1e8` 直接 400。
- **不再自动分窗**：同日早些时候落地的"一次采集 + 后台自动分窗"（`e5e1fac` 把上限放到 4 s /
  21 亿样本，`0513f84` 把分窗固化进服务端）**同日废止**。原因：1 s 的采集解码实测要
  **10~30 分钟**（CSV ≈2.4 GB），用户判定不实用；200 ms 是仍能"一次采完、一次解完"的完整窗口。
- **旧记录仍然可读**：`export_slices()` / `finalize_slices()` / `slice_merge.py` 保留，只用于读取
  与离线重建历史长窗记录（`streamed.schema=3`），不再由 `/api/capture` 触发。

## 5. 失败根因（**包地前**口径）：TRACECLK 2 ns 毛刺造成的 nibble 位移

> ⚠️ 本节是 **2026-10-18 13:xx（TRACECLK 尚未包地）** 的结论与数据。用户随后给 TRACECLK
> 包了地线，阈值口径已修正为「**0 ns 不行、≥2 ns 可行、4 ns 安全边际**」，见 **§6**。

- **现象**：0.2 s（500 MSa/s）采集在严格帧校验处失败，例如 `capture-1e205091e5de48e29f9ff8e14c8be225`
  在 312,299 B 处拒绝拼接（帧内读到 `FF FF`）。
- **根因**：TRACECLK 上的 **2 ns 宽毛刺**把半个时钟周期切成 3 段（实测 8/2/6、10/2/6、12/2/2 ns）；
  4 位 DDR 每多 2 个跳变就多 1 个字节 → **TPIU 帧对齐偏移 1 字节** → 严格帧校验失败。
  毛刺时间坐标**自首个时钟边沿起**（≈绝对时间 +10 ms）：首个毛刺 10.4096 ms 与 demux 报错
  偏移 312,299 B（10.4097 ms）吻合。
- **A/B（包地前，同一份 CSV 只改 `glitchNs`）**：
  | glitchNs | 结果 |
  |---|---|
  | 0 | 失败，偏移 312,299 |
  | 2 | 仍失败，偏移 632,831（**当时钟线毛刺未处理**，2 ns 不够） |
  | 4 | 通过，frames 24,593、errors 0 |
  另一份当时 `glitch=2` 失败的记录（`capture-2265…`）用 4 ns 也能解；本次验收记录**去掉滤波同样失败**
  （phase0 偏移 1,625,363、phase1 无 FSYNC）。**这些"2 ns 不够"都是包地前的时钟线口径**——
  包地后 2 ns 已足够（§6.2），4 ns 只作安全边际。
- **口径提醒**：`glitch=4` 的重跑"不再报错"**不等于单源干净**——`capture-1e205…` 用 g4 重跑仍有
  少量非 ETM 源帧（`streams={2:365403, 79:293, 3:120}`），`capture-2265…` 也有 `79`；
  **只有本次验收记录是单源**（`id_changes=[2]`）。
- **结论**：失败与 `fraction`（0.25/0.5）、`sync` 开关、ETM 选项（`0x11` vs `0x1011`）无关，
  只与毛刺/滤波有关；这是**信号质量 + 滤波前置条件**，不是 200 ms 上限或解码器能力限制。
  包地复测后时钟侧毛刺已归零，但数据线仍有 ≤2 ns 窄脉冲 → 阈值口径见 §6。

## 6. 包地复测（2026-10-18 14:11–15:00）：时钟毛刺归零，数据线仍需 ≥2 ns

用户把 **TRACECLK 时钟线用地线包覆**后，用同一套 200 ms / 500 MSa/s 流程复测
（记录 `capture-a856e7f9fc84460a88b296f2bd74c2b7`，glitchNs=0）。完整报告与机器可读汇总在
`docs/validation/20261018-200ms-grounded-clock/`（`report.md`、`acceptance-summary.json`，gitignored）。

### 6.1 包地解决的是时钟侧

| 指标 | 包地前（`capture-1e205…`） | **包地后** |
|---|---:|---:|
| TRACECLK 毛刺事件（同 2M 行窗口） | 45 | **0** |
| TRACECLK 毛刺事件（整份 200 ms） | 506（13M 行口径） | **0**（12,000,307 个时钟跳变，≤12 ns 间隔全为 0） |
| 2 ns / 4 ns 滤波删除的 CH0 跳变 | 1138 / 1254 | **0 / 0** |
| `irregular_half_periods` | 2450 | 20（都是**变宽**间隔，非窄脉冲） |
| 采样余量（4 ns 后） | 0.0 ns | **2.0 ns** |
| TPIU 解复用（不加滤波） | ❌ 失败 @312,299 / @1,625,363 | ✅ **通过**：24,567 帧、errors 0、`id_changes=[2]`、id2=**365,434 B** |

解复用在 glitch **0 / 2 / 4** 下结果**完全相同**（frames 24,567、errors 0、单源 ID 2、365,434 B）
——**滤波已不再是解复用的前提**。

### 6.2 但数据线 D0–D3 仍有 ≤2 ns 窄脉冲：0 ns 完整解码出 8 个包问题

同一份 CSV 只改 `session.json` 的 `glitchNs`（CSV/KVDAT 硬链接，**不是重新采集**）：

| 记录 | glitchNs | packetIssues | 指令 | 周期 | gaps / unknownExecution | ETM 流 |
|---|---:|---:|---:|---:|---|---|
| `capture-a856e7f9…` | 0 | **8** | 3,649,003 | 11,302,629 | 4 / **1807** | 基准（365,434 B） |
| `capture-123ef22…` | 2 | **0** | **3,675,419** | **11,399,057** | 1 / 0 | **与 4 ns 逐字节相同** |
| `capture-ea97a01…` | 4 | **0** | **3,675,419** | **11,399,057** | 1 / 0 | 与 2 ns 相同 |

- 0 ns 的 8 个坏包 = 3 簇（偏移 166,098 / 230,681 / 319,876）`I_RESERVED` + `I_BAD_SEQUENCE [I_EXTENSION]`；
  字节级只差 **8 个字节**：5 个包载荷（`fd→fc`）＋ **3 个结构字节（`0f→0d`）**，后者的偏移与坏包簇
  相差 8 字节 —— 数据线窄脉冲把 3 个 nibble 采错，解析器随后把后续字节误当新包头。
- 2 ns 滤波删除的数据跳变：CH2 **110** / CH3 **12** / CH4 **4310**（CH0、CH1 为 0）；
  4 ns 删 132 / 12 / 4338。**2 ns 与 4 ns 解出的 ETM 流 365,434 B 逐字节相同**，4 ns 相比 2 ns
  多删的跳变（CH2 +22、CH4 +28）对结果没有影响。

### 6.3 修正后的阈值口径（本文以此为准）

- **0 ns 不行**：数据线 ≤2 ns 窄脉冲会让完整解码出 8 个包问题（指令少 26,416、未知执行 1807）。
- **≥2 ns 可行**：2 ns 已修好这份采集的全部错字节，结果与 4 ns **逐字节相同**。
- **4 ns 是已验证的安全边际**：包地前的脏会话里 2 ns 仍失败（偏移 632,831）、4 ns 通过；
  页面默认保持 **4 ns**（相比 2 ns 多删的跳变对 ETM 流无副作用）。
- 不要再写"必须 4 ns / 2 ns 不够"——那是**包地前**的时钟线结论（§5）。

### 6.4 本次复测的局限

- **单次采集**（1/1），未做重复性；环境（室温/线缆姿态）未记录。
- 2 / 4 ns 是**同一份 CSV 的复滤解码**（复制记录 + 改 `session.glitchNs` + CSV 硬链接），
  **不是重新采集**——好处是排除采集会话差异，代价是没验证"重新采集 + 4 ns 仍 0 包问题"。
- 只测 200 ms / 500 MSa/s / TRACECLK 30 MHz / RS+CC；更高速率下的阈值未测。
- 2 ns 只在这份 CSV 上验证过（历史会话 glitch=2 仍失败），所以默认值仍取 4 ns。

## 7. 局限与未覆盖

1. **1 次成功**的 200 ms 采集，未做 3 次重复性验证。
2. 验收走**探针直连 + `/api/capture`**（与页面 `sync` 分支同一段 `target.js` 代码、同一 API），
   **未在浏览器里点页面**；浏览器侧另需用户完成首次 USB 授权。
3. **入口断点未启用**：`0x0800b48` 在当前 `fw.elf` 里是数据区（`runTo` 会超时），正确入口是
   `trace_hook_entry = 0x08000b51`。
4. **4 ns 是当前接线/LA 的经验阈值**（§6.3），更宽毛刺仍可能失败；**若要让 0 ns 可用**，下一步应给
   数据线 **D0–D3 也做包地/缩短回线**，再复测 0 ns——本次只包了 TRACECLK，数据线仍有 ≤2 ns 窄脉冲。
5. **200 ms 里有 10 ms 是触发前**（核暂停、无 trace），真实 trace 覆盖 **190 ms**；要"触发后满
   200 ms"必须**改触发位置或加深深度**——`do_export(time_span=(0, seconds))` 只能去掉触发前的
   10 ms，缓存本身只到 +190 ms，补齐不了。
6. 验收用的 `8891` 服务**已停**（复核时 8891/23367/8768 均无监听）；需要再看页面时按
   `report.md` §4 一条命令重启：`python -X utf8 tools/dev/serve-etm.py --etm-root ..\etm --port 8891`。
