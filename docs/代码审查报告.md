# 第三轮代码审查报告（2026-10-01，本人逐行精读）

范围：daplink 全链（dap/、swd_host/、riscv/、usb/、rtt/、scope/、api/、led/、main、boards）+ spi_bridge（含 SPI2 迁移 5 连击 f98c297..ec18c25 这些未审查过的新提交）。DFU 按约定不审。前两轮已处置项不重复报。

**总体结论**：前两轮的修复全部核实仍在位（含 SPI2 迁移相关的 CPHA/QSPI addr/辅助脚消毒）；spi_bridge 的帧解析、代数机制、DMA/临界区、时钟扫描等核心逻辑未发现新的 P1/P2。但本轮在 **HID 0x32 采样配置面**发现一个前两轮"主机输入面"清剿漏掉的 P1（变量 size 未验证 → 越界写），另有一个不对称的缓冲泄漏 P2 和一批 P3（协议漂移、死代码为主）。

## 一、P1（1 项）

**1. HID 0x32 CONFIG 的变量 size 未验证 → `s_stage` 越界写**（`api_param.c:483` + `scope_sampler.c`）

`vars[i].size = p[4]` 把主机报文里的 size 字节**原样收下**（只有 nvars/period 有钳位）。`scope_make_plan()` 用它直接生成 span（len 可达 255、4 字节对齐后 256），`scope_read_span()` 把 `sp->len` 字节读进 `s_stage[SCOPE_SPAN_MAX+4 = 68 B]`：

- SWD 后端：`swd_read_block4()` 放行（256 % 4 == 0 且不跨 1 KB 页）→ `swd_read_block` 按 64 字写 → **越界写 ~188 字节**（.bss 邻接静态区，随链接布局可砸中任意相邻全局变量）；
- RISC-V 后端：`riscv_jtag_read_once` 对齐路径按 words×4 写，同样越界。

触发只要两条 HID 报文：一条 CONFIG（nvars=1、size=0xFF）+ 一条 BENCH（action 8 不需要 START 就会采样）。主机面 = 浏览器页面（WebHID）/任意本地脚本。这与前两轮修掉的 raw 通道 24 B 缓冲、Transfer count 打穿是**同一类**输入面漏洞，采样配置面被漏掉了。

修法（一行/变量）：`scope_sampler_configure()` 里对每个 var 校验 `size ∈ {1,2,4,8}`，不合法**整包拒绝**（状态字回报错误），不要试图"钳到最近的合法值"（半解析的 plan 更难查）。

## 二、P2（1 项）

**2. `scope_push_def` / `scope_push_stat` 的端点写失败会泄漏包缓冲**（`scope_sampler.c:387`、`:417`）

`#12` 修复只改了 `scope_push_packet`（检查 `usbd_ep_start_write` 返回值、失败不记账、样本计入 usb_drop），但 DEF 包（每次 START 发一张）和 STAT 包（每 64 包一张）这两处**先记账（s_tx_busy/s_inflight/s_if_count）再调用且不看返回值**。在 USB RESET→CONFIGURED 的窗口里推送失败（端口层返回 -2，`usb_dc_hpm.c:241`），完成回调永不来，这个缓冲就永久占死；STAT 的节奏下窗口内累计 8 次即推流停摆，须 STOP/START。修法照抄 push_packet：失败则不记账、计入 usb_drop。

## 三、P3（择要）

**spi_bridge（SPI2 迁移后新代码的遗留）**
- `spi_bridge_proto.h:194` 的 `cs_policy` 注释与实现矛盾：注释"0=硬件 CS0 自动；1=辅助 CS 自动；2=手动"，实现（`spi_bridge.c:667/691-703`）实际是 **0/2=PB10 GPIO（0 自动包裹、2 纯手动）、1=辅助脚、3=硬件 CS0**——硬件 CS0 这个第 4 值没写进 proto。proto 自称"唯一真源"，测试脚本 choices=[0,1,2,3] 已经知道 4 值。改注释即可。
- `SB_F_CS_OFF`（proto.h:68）固件零引用（XFER 收尾只看 `SB_F_CS_HOLD`，`spi_bridge.c:1385`）。行为与"默认释放"巧合一致，删掉或注明。
- "EasyFlash 旧配置残留"防御防的是**不存在的路径**：ENV 里只存 `api_param_t`（LED/VREF，`api_param.c:163`），`sb_cfg_t` 从不持久化，每次上电都从 init 默认值开始。防御代码无害但注释误导；同时暴露一个不一致——**若将来真加持久化，pad_dc/rst/bl/te 有 `sb_pad_usable` 过滤而 pad_cs_aux 没有**（`spi_bridge.c:692-694` 直通 `sb_pad_of`），会留洞。
- `spi_bridge_init`（:1995-1999）的默认辅助脚还是 SPI1 时代旧值（DC=PB11/RST=PB12/BL=PB13/**TE=PB10**——全踩在 SPI2 信号脚上），靠 apply 时 `sb_pad_usable` 全过滤成 0 才没出事。与 tools 的新默认（PA02/PA31/PA10/none）统一掉。
- `SB_WOULD_BLOCK`（:107/:1624）死代码（无人返回）。
- `SET_PROFILE`（:2379-2405）里"quad 下退掉 PA30/PA31"的补救块已死：f98c297 删掉 `sb_pad_ok` 的 quad 规则后 validate 不再因这两脚失败；且 validate 失败时 `s_prof` 已赋值、不给主机报错——静默。
- XFER 的 `addr_len`/`dummy` 未按协议注释钳位（0..4 / 1..4），255 也接受，进 `sb_spi_apply_format` 把 addr_len_in_bytes 配到 255（寄存器字段截断，线上垃圾，无内存安全问题）。
- `PIN_CFG` 未知 line 号（default）不报错、仍走 validate + `sb_apply_aux_pins()`——会把辅助脚重驱回空闲电平（主机刚用 GPIO 帧拉低的 RST 会被拽回去）。default 应直接回 RANGE。
- `SET_CFG`/`SET_PROFILE` 在 USB ISR 里 32/16 B 结构体赋值 vs 主循环帧执行的并发读（P2-4 下沉修复的残余，窗口极小）。
- quad→非 quad 切换后 PB14/PB15 不解除 SPI2 复用（pinmux 只在 quad 时配置）。

**DAP/USB/RTT/scope**
- `usb_composite.c:876-888` QueueCommands 扫描：上游在 n==IndexI 时等待下一包（RTOS flags），这里等待被注释成空 if——纯 QueueCommands 流会以陈旧缓冲内容续扫，可能把正在 DMA 接收的缓冲首字节改写成 0x7F 并执行陈旧命令流。建议 n==IndexI 时 break。
- `cdc_interface.c:21-22` 文件头注释还停留在"evklite: UART3 on PB15/PB14"（UART2 迁移前）。
- `cdc_interface.c:580` `word_length = bDataBits - 5` 未校验（bDataBits=0 下溢成 251，寄存器字段截断）。
- `RTT_ACT_PEEK`（api_param.c:303）是"任意地址读探针自身内存"的常驻诊断后门（有意为之，浏览器页面可调）——建议在交接文档标注。
- `swd_host.c:715` `swd_write_debug_state` 为 static 零调用（其消费者 syscall exec 移植时已裁掉），`swd_read/write_core_register` 仅被它引用——裁剪残留，建议连 `DEBUG_STATE` 一起删。
- `riscv_svc` 的 RBENCH/WBENCH bytes 只钳 ≤1024 不强制 4 对齐：read 对齐路径按 words×4 写 stage（s_stage 内安全）、write 尾部半字把高字节补 0 **写穿到目标**（bench 写的是主机自选 scratch 区，无害）——若将来把这两个 API 用于正式数据面必须先收紧。
- `riscv_svc.c:37/318`：action 执行期间（可达秒级）HID ISR 写入的新请求会在 poll 收尾 `s_pending=0` 时被静默丢弃（主机协议等完成再发则无影响，可加 dropped 计数）。
- `riscv_jtag.c:703` `uint8_t tail[4]; (void)tail;` 死变量。
- `DAP.c:104` `Set_Clock_Delay` 每次改速 printf 到 console（量小，噪音）。

**2. DAP_JTAG_Configure 设备数无上限**

**3. HID RTT raw 透传：24 字节响应缓冲可被同一引擎打穿 + 漏作废影子缓存**
`rtt_bridge.c:884-893`：`DAP_ExecuteCommand(s_raw_req, s_raw_rsp)` 的响应缓冲只有 24 字节——raw 请求首字节发 `0x7F`（ExecuteCommands）或一条大 count Transfer，响应就远超 24 B，越界覆盖邻接静态变量（`s_start_pending` 等）。另外这是**唯一**“主机碰 DAP”却既不调 `rtt_bridge_note_dap_activity()` 也不刷新 `s_last_dap` 的入口（主通路 `chry_dap_handle` 每条命令都调），主机经它写了 DP_SELECT/AP_CSW 后，scope/RTT 还拿旧影子缓存 → 静默读错地址。修复：执行前后各加一次 `note_dap_activity()`，并把 raw 通道限制为单命令或扩缓冲到 `DAP_XFER_SIZE`。

**4. `scope_run_bench()` 在无空闲缓冲时指针越界（本次新发现）**
`scope_sampler.c:644-646`：`uint8_t *dst = &s_pkt[s_fill_buf][SCOPE_HDR];` 在函数入口无条件取址，而 `s_fill_buf` 合法值含哨兵 `0xFF`（“没有缓冲”）。8 个包缓冲全部在飞（例如主机停止读 0x83 后停采样，再点 action 8 标定）时，`s_pkt[255]` 是越界指针，`scope_sample_bytes()` 随后按 `iters`（上限 100000）× 帧字节往里写——持续的越界写。修复：取址移到 `s_fill_buf < SCOPE_TX_BUFS` 判断之后，或先 `scope_alloc_buf()`。

**5. `swd_write_ap` 影子缓存在传输成功之前更新（J-Scope 新代码）**
`swd_host.c:259-288`：`case AP_CSW: dap_state.csw = val;` / `case AP_TAR: dap_state.tarp = val; tarp_ok = 1U;` 都在 `swd_transfer_retry` **之前**执行，失败路径 `return 0` 不回滚。下一次调用看到缓存命中就跳过写入，而硬件里还是旧值——瞬时 WAIT/FAULT 一次之后，`swd_read_word_hold_prepare()` 以为“抱住了 TAR”，实际 TAR 已被自增带跑，**采样数据静默错位**（不报错、看起来正常）。修复：缓存更新移到传输+RDBUFF 确认成功之后，失败分支顺手 `swd_invalidate_ap_cache()`。对照 `swd_write_dp`（212-214 行）就是只在成功后更新的正确写法。

**6. `DAP.c:1066` 拆分 SWD_Transfer 时漏改的调用点**
`response_value = SWD_Write(DP_RDBUFF | DAP_TRANSFER_RnW, &data);` —— 把 RnW=1 的读请求喂给了写引擎：ACK 后主机照样强驱 SWDIO 数据相位（与目标争总线，靠串联电阻苟活），且 `data` 是未初始化栈值，作为“上一笔 posted 读结果”进响应。同源问题 `DAP.c:1387`（JTAG 版）。上游此处是统一的 `SWD_Transfer()` 按 RnW 分派。修复：分别改 `SWD_Read(...)` / `JTAG_Read(...)`。

## P2 —— 边界情形 bug / 可靠性

**7. `rtt_bridge_stop()` 恢复 UART 数据源不做 resync（本次新发现）**
`cdc_interface.c:113-120`：`uartx_set_cdc_source(0)` 只清标志。桥运行期间 UART RX DMA 一直 infinite-loop 转着（`rb_write_pos` 停在旧值），停桥后第一次 flush（`uartx_rx_flush_locked`）把期间攒下的字节——长时间桥接后可能超一整圈、是任意陈旧混合——一次性灌进 CDC 环送给主机。对照：`chry_dap_usb2uart_set_enabled(1)` 的恢复路径就调了 `uartx_rx_resync()`（`usb_composite.c:851`），这条路没有。修复：`rtt_bridge_stop` 恢复源时同样 resync。

**8. `rtt_swd_set_clock` 判错下标错误**
`rtt_bridge.c:220`：`return (s_resp[2] == DAP_OK)`——SWJ_Clock 的状态在 `s_resp[1]`；`s_resp[2]` 靠静态零初始化“恰好等于 DAP_OK”恒判成功，真正的失败会被漏判（连 `-1` 都不报，斜坡逻辑失去失败感知）。

**9. JTAG_Sequence 硬编码 45M blob、delay 恒 0**
`JTAG_DP.c:43`：`JTAG_Sequence_GPIO_ASM_45M(info, tdi, tdo, 0)` 完全无视 `DAP_Data.clock_delay`，`JTAG_Sequence_Slow` 是死代码。低速 JTAG 目标的 TAP 复位/IR 扫描（都走 sequence）会以 ~45M 时序跑，失步风险；README 把“`adapter speed` 对 JTAG 无效”记为已知坑，但这是缺陷不是特性（SWD 侧同一问题已经用档位分派修好了）。

**10. SWD 主机通路 bit-bang 无中断保护（子代理发现，待验证）**
`swd_host_port.c:54-62` 只有 swd_host 通路（桥/采样器）用 `disable_global_irq` 包住位翻转；DAP 主机通路 `DAP.c → SWD_Read/SWD_Write` 直调 blob 无保护，blob 内部的 `csrrci` 已被注释（`SW_DP_GPIO_ASM_SLOW.S:164`）。36 MHz+ 档主机 bulk 传输被 USB/CDC ISR 打断时 ACK 采样错位，与桥/采样器可靠性不一致。建议把临界区下沉到 `SWD_Read/SWD_Write` 让两条通路共享。

**11. USB RESET 后 DAP 队列索引不复位（本次新发现）**
`usb_composite.c:447-487`：RESET 事件只清 3 个 idle 标志，`USB_RequestIndexI/O`、`USB_RequestCountI/O` 及 Response 侧四个计数全部保留；而 CONFIGURED 固定武装 `USB_Request[0]`。运行中总线复位（主机驱动重初始化、睡眠唤醒）后，`dap_out_callback` 用旧 `IndexI` 做 TransferAbort 判断（读的是旧缓冲），数据却落在 [0]——DAP 命令流错乱直到再次复位。修复：RESET 时把两组 index/count 全部清零。

**12. `usbd_ep_start_write` 返回值全程忽略**
`usb_composite.c`（CDC IN，561-580、899-910）与 `scope_sampler.c`（316-320、362-366、391-397）：端点写失败（断开、stall）无任何反馈——CDC 侧 `usbtx_idle_flag` 卡 0 永久停流；scope 侧 FIFO（`s_if_count`）与真实在飞脱钩。现有的“丢拍缓解”只覆盖缓冲忙，不覆盖 start_write 本身失败。至少在 `scope_push_packet` 检查返回值并回滚 `s_if_count`/`s_tx_busy`。USB 重新枚举时 armed 的 0x83 传输不完成、8 个缓冲永久泄漏也属同类（表现为重枚举后 usb_drop 狂涨，STOP/START 可恢复）。

**13. `vfat.c` fat_next 无界读（bootloader，恶意/垃圾 FAT 链）**
`vfat.c:326-332`：`s_fat1[cluster * 2]` 对 cluster>255（s_fat1 只有 512 B）越界读，cluster 来自主机写的 FAT/根目录项。正常拖入的固件用簇 5..36 无碍；恶意链值可读越界最多 ~128 KB 静态区。修复：`cluster > 255` 直接返回终止符。flash 写入路径本身我核对过是安全的：`APP_MAX_SIZE` 双重钳制 + erase 上界，参数区（0x800FE000 起）和 bootloader 都不可能被 MSC/DFU 写到。

OpenOCD 自己的连接不受影响（本轮 8 个档位全部 `verified`），范围限于 raw 通道；测试脚本已改成

## 二、新发现

### P1

**1. `riscv_jtag_hold_read` 的周期性 SBCS 错误检查会静默毁掉每第 32 个样本**（`riscv_jtag.c:598-611`）

DMI 流水线是“本次扫描返回上一次请求的结果”。每 32 拍的检查调 `sba_check_errors() → dmi_read(DM_SBCS)`（`riscv_jtag.c:263-266`），而 `dmi_read` 的第一个 `dmi_post` **显式丢弃 pending 响应**（注释原话 "flush any pending response"）——在流水模式下那正是上一拍 SBDATA0 读的真值，本该由本拍交付。随后本拍的 `dmi_post(READ SBDATA0)`（611 行）返回的是那个 NOP 的响应：op=SUCCESS、data 无意义，却被当作样本值写进上一拍的槽位。

后果：RISC-V 单变量快路径下**每 32 拍静默损坏 1 个样本（≈3.1%），无任何错误计数**。bench（action 8）只测时间不验值，所以没暴露。修法（保持两次扫描、零损失）：检查拍改为 `post(READ SBCS)`（返回值 = 上一拍样本，照常交付）+ `post(READ SBDATA0)`（返回值 = SBCS，用于检查）；本拍不返回值，下一拍自然收回刚投出的 SBDATA0 读。修完建议在 RISC-V 靶上跑一次端到端 tick 斜率 / u_hi 高位校验（SWD 侧已有同款验收）。

**2. raw 通道挡截的假设不成立：`DAP_Transfer` 与 `SWD_Sequence` 仍可打穿 1 KB 响应缓冲**（`rtt_bridge.c:762-772`）

入口检查的注释假设“其余命令的响应长度天然被 24 字节请求长度限死（最坏 Transfer 带时间戳 3+20×8=163 B）”——**不成立**：count 是请求里*声明的*字节，handler 不会按请求实际长度截断。`TIMESTAMP_CLOCK=24 MHz` 是启用的，一条 24 字节请求 `[0x05, 0x00, 0xFF, 0x13, …]`（count=255，每项 RnW+APnDP+TIMESTAMP）的响应是 3 + 255×8 = **2043 B**，越界写约 1 KB（伴随 handler 逐项读越过 `s_raw_req[24]` 的越界读）。`SWD_Sequence(0x1D)` 同类（DIN 响应累计可达 ~2041 B）。修：`0x05` 的 count 钳到 (1024-3)/8 ≈ 127；`0x1D/0x14` 拒绝或按请求长度钳；更稳的是给 raw 通道做命令白名单。`dap_raw_boundary_test.py` 补这两条用例。

### P2

**3. SPI 桥 DMA 通道泄漏**（`spi_bridge.c:708-714`）

`sb_dma_init()` 在 `s_dma_ok` 已为 1 时（再次 ENABLE=1，或 enabled 状态下 SET_CFG / SET_PROFILE 都会重走 `sb_spi_hw_init`）直接 `memset(&s_dma)` 后再 `dma_mgr_request_resource`，**旧通道没有 release**——每次配置泄漏一个 DMA 通道。池本来就小（CDC 已占 2 个），几轮重配后申请失败、桥静默退回轮询且重启前无法恢复。修：入口先 `if (s_dma_ok) dma_mgr_release_resource(&s_dma)`。

**4. SPI 桥控制面在 USB ISR 里做重活、与在飞事务零互斥**（`api_param.c` CMD_SPI → `spi_bridge_hid`）

ENABLE/SET_CFG/SET_PROFILE 在 HID ISR 里同步执行 `sb_spi_hw_init`：7 时钟源 × 32 分频的扫描、SPI 复位轮询（10 万次循环）、DMA 申请——ISR 可达数百 µs 以上，期间 DAP/CDC 全停。更实质的问题：若主循环正在 `sb_spi_xfer` 的 **CS 窗口中间**，ISR 重配 SPI 格式/时钟/换 DMA 通道会当场打断该笔事务（表现为偶发 TIMEOUT/DMA 错）。建议照 RTT/scope 的做法把这三个动作改成 pending 标志、主循环执行。

### P3（择要）

- `spi_bridge_poll` 的 `s_reset_req`/`s_abort_req` 清环不在临界区，与 `spi_bridge_out_done`（ISR）的 `s_out_w/s_out_used` 更新交错理论上可丢一帧（窗口极小）；顺带 **ABORT 没有清 IN 队列**，与 proto 头“丢弃未处理帧与 IN 队列”的注释不符。
- 协议漂移：`SB_F_CS_AUX`、`SB_F_NO_DMA` 有实现但 `SB_F_CS_AUX` 实际被忽略（CS 由 cs_policy 决定）；`cs_hold_in_step` 字段未用；~~`sb_cfg_t` 实际 28 B~~ **订正：实际 32 B（尾部 `reserved[4]`），proto 头注释"总长 32 B"本来是对的 —— 上一条是我数错了，加 `_Static_assert(sizeof(sb_cfg_t)==32)` 时当场被抓**（测试脚本按显式偏移打包，没踩坑）。
- `sb_delay_us` 的 u64→u32 tick 截断：DELAY 帧 ≥ ~179 s 会变短（面板场景无害）。
- `riscv_jtag.c` 里 `SBA_CFG_RECHECK` 宏与“③每 4096 次强制重配”的注释是已废弃方案的残留（实现已改为只在安静点重配，是对的），建议删掉避免误导。
- scope RISC-V 后端自动回退：JTAG-only 目标上先撞 SWD 路径会触发 `swd_init_debug` 的 nRESET 硬复位（DAPLink 既定行为），可能把目标复位了；建议记住上次成功后端或文档标注。
- scope bench 在 running 且有空闲缓冲时仍会写进正在填的包缓冲（污染在飞流，非内存安全）——上轮 P3 残留。
- PINTEST/WIGGLE 诊断在 USB ISR 里跑长循环，且桥未使能时也会动 SPI 引脚。
