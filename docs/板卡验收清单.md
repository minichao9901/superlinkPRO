# superlinkPRO 板卡验收清单

**审核稿。** 每块板先按声明支持的能力选用例，再按「功能」「性能」分别出结果。Fxx、Pxx 用于归类，带小数点的编号用于定义用例。实际验收以「用例 × 条件」为最小单位。每行只有一套条件、一个主判据和一个结论。功能行核对行为和数据，性能行给出一个有明确计量口径的指标。一次采集可以给多行提供证据，分别判定。历史报告按分组给出的结论须逐条核对到同条件证据才能引用。

**开测前登记**

| 登记项 | 必填内容 |
| --- | --- |
| 版本和对象 | 板卡与芯片修订、目标核、探针型号/序号/硬件/固件、工作台版本/源码提交、实际 EXE 与 ZIP 指纹、Wasm 版本、系统与浏览器版本。注明源码页、冻结包、原生 USB 或模拟路径 |
| 板卡画像 | 电源、地线、USB、SWD/JTAG/NRST/LA 接线、夹具和 CFG/ELF/BIN 指纹、CPU/TRACECLK、请求频率及实际频率来源、允许的操作、数据范围和回退方法 |
| 范围和门槛 | 给展开后的每条用例标为「必测」「按能力选测」或「探索」，写明实际参数、轮数和阈值。对已声明支持的功能，缺接线、夹具或授权时登记阻塞。按批准的能力范围冻结矩阵，记录选用和排除的组合及原因 |
| 资源与恢复 | 确认板卡、探针、串口、LA 空闲，单执行页独占。写入前验证备份长度和 SHA-256，划定 RAM/Flash 测试范围、选项字节、校准区和其他保护区。切换夹具后先回读启动标记、时钟和专属变量或控制块 |

工作台从 `catalog`、`ping`、`page <分类> describe/state` 开始，按当前页面的控件与方法操作。CLI 接单后继续核对任务、硬件状态与产物。超时按 job ID 核对当前状态，确认后再决定是否重试。 [统一 CLI 指南](toolbox-cli-ai.md)

H743 的 SWD／ARM JTAG 和 HPM6800EVK 的 RISC-V JTAG 同板复测，按已验证版本、计数口径和待复测条件索引。 [实机收尾与复测经验](validation/h743-hpm6800evk-closeout-20261114.md)

每条子项填「通过」「失败」「阻塞」「未测」或「不适用」。实际达到测试条件后违反门槛填失败，条件无法建立填阻塞，计划内尚未执行填未测，声明能力范围外填不适用并写明依据。若功能的判据就是设备能建立请求档，降档即该功能实例失败。首测性能缺少已批准门槛时填「基线已测，待定标」。按功能和性能分别汇总各状态的数量及实例 ID，必测实例全部通过才判该范围通过。复测追加结果并保留首次失败证据。

用例实例以 **子项 ID／后端／条件档** 唯一标识。结果行填写 **实例｜必测性｜固定条件及轮次｜请求／生效／实测档｜主判据及数值门槛｜实测值及错误计数｜结论｜证据与 ISSUE ID**。条件档包含会影响判定的参数及夹具编号。表中出现「分别」「各」或列出多个档位、动作、格式、统计对象时，每个选中的取值都要建行。范围内未执行的行预先建好并标「未测」。省略某一组合时记录原因。证据至少包括命令或操作、参考值、实际值、计数和可追溯的报告小节或文件指纹。测不到的计数填「不可观测」并注明原因。若该计数是主判据的必要证据，结论填「阻塞」。

**从矩阵生成报告。** 为每个分组标记覆盖范围，再按上表和分组中的条件表建立实例行。以 J-Scope 为例，Chrome 八路 14 µs 的「实际时长」「调度跳拍」「USB 丢样」「尾差」各有独立行，提前结束的窗口仍可用于对应短窗判定。RTT 的 45 MHz 上行短窗可以同时给「内容完整」「吞吐」「读错误」取证，三个判据各有一行。各分组都按此方式出报告。

### F03 SRAM 和寄存器

SRAM/ILM/BRAM 按板型填写实际地址。读测试用 CPU 生成的固定模式或已独立验证的参考镜像作真值。写测试使用独占测试区，预先备份，写后在参考档独立读回并核对边界哨兵。模式默认取全零、全一、交错位及带固定种子的地址相关序列。

| ID | 子项 | 测试条件 | 验收标准 |
| --- | --- | --- | --- |
| F03.01 | 标量读 | 停机，访问对齐地址，8/16/32 位分别测，每种模式至少覆盖首、中、尾地址 | 每个值和字节序均与参考一致，无访问错误 |
| F03.02 | 标量写 | 停机，8/16/32 位分别测，相邻字节布置哨兵 | 请求范围逐字节匹配，哨兵不变，无写入错误 |
| F03.03 | 非对齐访问 | 针对接口声明支持的宽度，以基址偏移 1 字节分别测试读和写 | 支持的组合逐字节一致，声明拒绝的组合报错且哨兵不变 |
| F03.04 | 块读 | 停机，64 B 和 20 KiB 分别测，后者覆盖后端分块边界。各档位、各大小 3 轮 | 实收长度与请求相同，逐字节匹配，零超时、零重试 |

| F03.06 | 运行态读 | CPU 运行，使用只读稳定区及单调计数器分别验证 | 稳定区逐字节一致，计数器符合约定，目标继续运行 |
| F03.07 | 运行态写 | 目标声明支持，写入夹具专门预留的邮箱，由目标回传确认 | 目标确认值与主机写入一致，目标继续运行，保护区不变 |

## 二、性能

开测前按每个 ID 和条件登记数字门槛。吞吐、采样率用下限，延迟和资源用上限，质量计数用允许上限。优先用板卡规格或已批准的专项门槛。审核稿暂用以下定标方法，基线须匹配板卡、夹具、负载、实际档、后端和计时边界。

| 指标 | 审核稿默认定标方法 |
| --- | --- |
| 吞吐、采样率 | 短窗中位数或单次长窗实测值 ≥同条件、同统计量验收基线的 90%。明确可用额定速率定标时，使用该用例的专用下限 |
| 延迟、耗时 | 表中指定的 P95、最大值或中位数 ≤同条件、同统计量基线的 110% |
| 峰值资源 | 峰值 ≤同条件峰值基线的 110%，并满足已设定的资源预算 |
| 正确性和丢失计数 | 按该行写明的值逐轮判定。基线为零时使用绝对上限，禁止计算相对偏差 |

无合格基线或板卡阈值的首测填写「基线已测，待定标」。审核确认后才用于判定。所有必测轮均须满足预设质量门槛。

每个性能实例开测前把「上限」「下限」换成实际数字并记录单位和来源。报告单独保留各轮原值。例如用毫秒报告 P95、用十进制 MB/s 报告吞吐、用组/s 报告采样率，不能跨单位或用峰值对照中位数。历史最佳先按相同条件和相同统计量配对，再计算 `(本轮值 ÷ 基线值 − 1) × 100%`。无匹配基线的对照行标「待定标」。频点档位、帧长、数据规模、统计窗口、计时边界或主机路径变化时，各自定标。

吞吐稳态默认 **3 轮 × 至少 8 秒**，预热单列。默认连续流档另做 **1 次连续 60 秒**，用首末有效时间戳核对实际窗口，停机排空单列。交互延迟默认每项 30 次，报告中位数、P95、最大值、失败和重试数，P95 取升序第 `ceil(0.95 × N)` 个值。非交互阶段耗时默认 3 次，记录原值和中位数。冷启、暖机及前台渲染模式分开。固定频率用例必须回读实际档并单列降档。计时注明从 CLI 提交、硬件开始还是页面事件开始，吞吐注明 KiB/s 或十进制 MB/s。夹具只提供相对时钟时，用同一时钟域计时或提供时钟对齐证据。

**F103ZE 专项指标。** SRAM 块读与块写、RTT 的 45 MHz 和 60 MHz 均为关键档，直接请求相应频点。使用同板、同负载、同后端、同计时口径的历史最佳已验证结果对照，逐档报告相对差值。吞吐或采样率低于对应历史最佳超过 2% 时进入定因和修复复验。超过历史峰值且数据完整性、持续时长和错误计数均达标时，记录为性能提升。频率证据分为请求值、固件生效档和引脚实测值，逐列记录来源，声明引脚物理频率通过时附测量及容差。J-Scope 单路与八路分别扫周期，寻找调度跳拍率严格低于 0.1% 且 USB、数据校验通过的最快实测档，并做连续 60 秒复验。

**F103ZE J-Scope 条件矩阵。** CPU 72 MHz、SWD 生效档 60 MHz、夹具 `scope72.elf`、flags `0xa1`。记录配置的 µs 值、回读周期 tick、探针时基、每组字节数及后端。按有效设备时间计算实收组率，审核稿暂以回读周期理论组率的 99% 作最低速率。每个档位按 P05.03–P05.06、P05.11、P05.15 分别出质量结果。

| 通道条件 | 默认连续档 | 高速扫点候选 |
| --- | --- | --- |
| 单路 u32，4 B/组 | 25 µs，60 秒 | 3、2.75、2.5 µs，再扫 57、56、55、54 tick，按需要向更短周期补点 |
| 八路连续 u32，32 B/组 | 100 µs，60 秒 | 21、20、19、18、16、15.5、15、14.5、14、13.5 µs，临界区按实际 tick 补点 |
| 八路分散地址 u32，32 B/组 | 100 µs，60 秒 | 独立扫点，记录分散布局和实际 tick，按自己的基线定标 |

扫点从慢到快，按实际周期 tick 去重并在边界补点。有效组是一个时间点的全部通道样本。组率使用同一窗口的 `(有效组数 − 1) ÷ (最后一组时间 − 第一组时间)`。按全宽快照分别取差值，组合计数和截断状态字只作辅助证据。先核算固件计数边界及主机可存样本量，达到容量上限而提前结束的窗口如实登记。最快合格结论限定在已测的后端、通道、档位和窗口。其他通道数、标量类型或地址布局按板卡能力登记，实测独立成行。 [J-Scope 协议与计数](../web/docs/scope-page.md) · [J-Scope 首轮](validation/f103ze-board-acceptance-web9-20261108.md#j-scope-补测) · [高速及长窗实测](validation/f103ze-night-acceptance-20261108.md#p05-j-scope)

例如对 **J-Scope／Chrome WebUSB／八路连续 u32／336 tick（24 MHz 时基下 14 µs）**，以下行各自出结论。原生 USB 的相同档另建全套实例。

**取证与清理**

1. 每轮优先使用仓库外的唯一临时目录，例如 `$env:TEMP/superlinkPRO-acceptance-<run-id>`，存放夹具副本、备份、日志、原始下载和导出。工具无法使用仓库外目录时，改用仓库 `tmp/` 下本轮独占的新目录，只给本轮子进程设置 TEMP/TMP。验收现成 EXE 直接使用指定包。需要隔离源码构建或修复时，才使用独立 worktree，构建与测试产物仍落在本轮临时目录。
2. 开测前保存 Git 状态与复用服务的数据目录清单。服务写入自己目录时，按本轮 job 记录新产物的 ID 和绝对路径。用 `batch` 执行批量请求，或在保存单条结果后 `ack` 回收。下载校验后释放本轮暂存的 Blob。
3. 按本轮实际修改的对象逐项确认 F10 的硬件恢复，核对任务回收及本轮服务退出。`docs/validation/` 只保留展开后的结果、质量计数、关键计时、失败摘要、必要指纹及获准留存的证据引用。已知问题更新原 ISSUE，首次发现的问题新增登记。恢复未核对成功时保留必要备份，正式基线按存储规范留存。
4. 成功、失败和取消后都按台账清理。先验证报告和证据引用，再核对真实绝对路径、归属和目录链接，只处理本轮可再生产物，优先移入回收站。若使用本轮 worktree，先确认它只含已提取的本轮修改与可再生产物，再用 Git 移除并核对 worktree 清单。以开测前的 Git 和服务数据目录清单对账，记录清理项数、释放字节、剩余路径和保留原因，再判 F10.07。 [问题跟踪列表](项目问题跟踪列表.md) · [存储维护](storage-maintenance.md)
