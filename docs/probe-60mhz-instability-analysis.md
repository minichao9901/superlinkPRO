# 探针 60 MHz 档"滑档到 45 MHz"的根因分析（2026-10-18）

结论先说：**物理链路在 60 MHz 上是能跑的；真正的问题是代码在"换档那一下"缺少收尾，
一次首发失败就把整场会话永久降到 45 MHz —— 属于代码缺陷，被 H743 在 60 MHz 的余量不足放大。**

## 1. 现象是怎么产生的（代码链路，逐行）

1. 页面请求 60 MHz → 固件 `s_swd_clock_req = 60 MHz`（每次 start 都从请求档开始：
   `rtt_bridge.c:549`）。
2. `rtt_swd_init()`（`rtt_bridge.c:249`）：
   - 4 MHz 完成 JTAG2SWD 握手 + DP 上电（L262-270）；
   - **斜坡**：切 20 MHz（`RTT_SWD_RAMP_HZ`，L74/L276）——注意这一句是
     `(void)rtt_swd_set_clock(RTT_SWD_RAMP_HZ)`，**返回值被丢弃**，斜坡失败无人知晓；
   - 再切到目标 60 MHz（L279），压回 `clock_delay` 覆盖值（L283-286）；
   - **首发探针**：读 DP IDCODE，只有 **2 次**尝试（L291-299），两次都失败 → `return -4`（L301）。
3. `-4` 被上层当成"该档不可用" → `rtt_bridge_link_recover()`（L515-528）
   **无条件** `rtt_clock_step_down()`（阶梯 `{60,45,36,30,20,10}`，L84）→ **60 降到 45**，
   再整条重走 `rtt_swd_init()`。于是页面显示"实际 45 MHz"，整场会话就停在 45。

## 2. 是信号质量还是代码？—— 五条互相独立的证据

| # | 观测 | 指向 |
|---|---|---|
| 1 | **稳态** 60 MHz 无损：`regression-swd` P2 60M = **2977 KB/s LOSSLESS**；读基准 3431 KB/s | 物理链路在 60 MHz **能连续跑干净** → 不是"眼图不够" |
| 2 | 失败**只发生在换档后的第一次访问**（scope START 60M 13%/670 次，45M 0/301） | 与速率无关、与**切换瞬间**有关 |
| 3 | 失败后 **0/2/5/10/20/50/100 ms 连探 18/18 全失败**，清 sticky 也不恢复 | 不是"偶发 ACK 抖动"，而是 **DP 状态机失步** |
| 4 | 只有**整条重走** `rtt_swd_init()`（= JTAG2SWD 线复位 52 高 + 0xE79E + 57 高 + DP 上电 + 斜坡）才恢复 | 失步需要**线复位**才能救 → 典型"过渡沿时序"损坏 |
| 5 | 失败后再 start 一次（重新 init）在 60 MHz **成功率 ≈ 87%** | 同一条链路、同一个速率，重 init 就通 → **不是速率上限**，是那次切换 |

⇒ **代码缺陷（换档收尾缺失）为主因**；H743 的 SWD 官方余量约 50 MHz，60 MHz 属**超规格使用**，
余量小到"任何一次过渡沿差错都兜不住"，这是放大器而不是根因。

另外 `fence.i` 已确认存在（`SWD_DynamicLoad_60M` 里 memcpy 后紧跟 `fence.i`，
见 `build_dfu_evklite/output/akaLinkPro_App.asm` @0x80038230），**"blob 装载后指令缓存没同步"这条已排除**。

## 3. 三个具体缺陷（按收益排序）

1. **换档后没有"收尾/静默期"**：20→60 切换完成后立刻发第一笔 DP 读（L288-299）。
   SWD 换频的通行做法是**先打 ≥8 个空闲 SWCLK 周期（或等几百 ns）**再发事务，
   让目标端采样窗口重新同步。现在完全没有。
2. **恢复策略只降不重试**：`rtt_bridge_link_recover()` 无条件降一档（L522），
   但证据 5 表明"同一档重 init"就能成功。改成**先同档重 init 一次、仍失败才降档**，
   60 MHz 的留存率可从 ~87% 提到接近 100%，转发吞吐从 **2.45 → ~2.9 MB/s**（+18%）。
3. **斜坡失败被静默吞掉**：`(void)rtt_swd_set_clock(RTT_SWD_RAMP_HZ)`（L276）。
   若斜坡没成功，等于 4 MHz 直跳 60 MHz —— 固件注释自己写了这条路"头几次访问就失败"（L272-275）。
   应改为检查返回值，失败则按 4→20 逐级重试。

## 4. 建议的验证实验（做一次就能定稿）

- **E1 留存率**：把"同档重 init"实现后，60 MHz 连续 start 20 次，统计降档次数（现在预期 ≈2~3 次，改后 0 次）。
- **E2 收尾期**：加空闲周期后再测 E1，若降到 0 → 缺陷 1 是根因；若仍偶发 → 缺陷 2 是主要保险。
- **E3 对照**：把页面请求改成 45 MHz 连跑 20 次（预期 0 次降档），确认阶梯表与测量口径没问题。

## 5. 已知的"不是问题"的部分

- 不是 USB/主机侧：HID 桥的 `rc` 与页面读数一致（`-4` 明确来自固件的 AP 验收读）。
- 不是探针固件版本问题：`3214872`（当前）已在 2026-10-04 的 `bbb86a8` 里加过 `rtt_bridge_link_recover()`，
  本分析针对的就是该机制本身。
- 不是时钟配置错误：capture 记录里 `coreHz=60 MHz / physicalTraceHz=30 MHz` 与设计一致（ETM 那条链）。
