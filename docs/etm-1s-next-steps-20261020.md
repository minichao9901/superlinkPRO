## 2. 本轮独立复核与必须先修的问题

本地证据：`E:/superlinkPRO/docs/validation/20261020-codex-ds-next-1685c01-6e93c42a/`。

### 2.1 查询计算量实证

使用现有 `tmp/p6b-scale/record-3x/store`，不修改原始记录。墙钟为不带 profiler 的一次请求；调用次数来自随后单独的 profile，不能混为同一耗时。

| 操作 | 不带 profile 的墙钟 | profile 发现 |
|---|---:|---|
| `window(0,199999)` | 1.994 s | `_expand` 200,001 次生成器进入/恢复，即约20万条逻辑事件展开 |
| `function_timeline(0,199999)` | 2.841 s | `_expand` 400,002 次，完整两遍 |
| `navigate(400000,-1,'instruction')` | 0.376 s | 展开64,323条事件，再选最后一个 |

把循环从字典查找改成局部变量无法解决这个数量级问题。查询应使用动态区间、检查点/导航索引和聚合，不应先完整恢复每条历史指令。

### 2.2 [P1] generation 改变后缓存返回旧结果

位置：`etm/tools/trace_store_adapter.py` 的 `ensure()`、`_cached()`、`window()`、`function_timeline()`。

`ensure()` 替换了 `_store`，但 `_windows/_timelines` 不失效，缓存键也没有 generation。最小复现：同一个适配器先查询 old generation，换代 new 后 active store 已是 new，window/timeline 仍返回 old。

修复要求：

- 缓存键必须绑定实际 store generation/必要版本签名；换代和关闭时清理对应缓存。
- 不能只补一句 clear：旧请求正在计算时，新 generation 可能已发布；旧请求完成后不得把旧结果写入新代缓存。
- 测试同一 record ID 重解码、同一范围不同结果、并发计算与换代、取消/失败保留旧完整代。

证据：`probe_cache.py`、`cache-result.json`；这属于已经复现的正确性问题。

### 2.3 [P1] 现有首屏判定遗漏默认轨迹图

位置：`etm/web/app/history.js`：`load()` 调 `render()`，`render()` 在请求页面前 await `renderTimeline()`；`view.js` 对 timeline 请求的超时为45秒。

因此大样本 timeline 约497秒时，实际网页会阻塞并可能超时。`open+overview+page≈0.51秒` 没有包括真实加载顺序，不能标“首屏达标”。全段 window 约376秒也超过现有180秒窗口请求超时。

修正：

- 报告将0.51秒明确改为“对象层部分请求”，完整首屏状态改为未通过。
- R1 给出快速默认 timeline 后按实际网页重新验收。
- 基础页和慢图可独立/并发载入，图表有明确进度且不挡住首批行；这只是可用性修复，不能把未完成轨迹图的预览当作完整首屏达标。
- 不把延长超时作为性能修复。

### 2.4 [P2] 大输入指纹被静默跳过

位置：`trace_store_adapter.py::_stale_inputs()`：`MAX_HASH_BYTES=64MiB`，大于该值时即使有 sha256 也只比较大小。

独立探针：声明错误SHA256的67,108,865字节 `native.bin` 被返回“无问题”。1 s 的 native 输入会进入这个范围。另需核对 `bindings.inputHash.skipped=true` 的 store 在正常浏览路径的处理，不能默认为已核验。

修复要求：去掉按体积静默降低完整性保证的行为。可以一次完整核验、构建时随读取计算、受保护的输入/代绑定、分块校验等方式减少重复读取，但要通过“同长度改写、mtime保持不变”的测试。`--no-hash-inputs` 可用于明确的诊断，不能混入最终用户性能/正确性验收。

## 4. R1：先让已有 store 查询可用

先使用现有200ms和规模store开发；不必等待新原生写出器或新的硬件记录。

### 4.1 必须替换的查询算法

- 正常 `window/timeline` 不调用 `TraceStore.events()` 全量生成事件字典，也不逐指令重放 CallTracker。
- 为动态区间建立可直接查询的映射：逻辑seq范围、静态plan/指令ID、执行状态、周期锚点、路径/调用状态引用。
- 完整覆盖的区间/块直接合并统计；只在窗口首尾、桶边界和状态变化边界做必要裁剪。
- 增加查询所需的**真正聚合信息**：函数/源码热点/执行状态/周期/路径贡献、事件位置，以及合并跨边界所需的首尾状态。当前AGG的总指令/状态计数不能冒充这些信息。
- 路径可用共享节点ID和路径变化区间；不要为每条指令复制字符串调用栈。
- 默认全段1600桶timeline在构建/索引阶段生成并持久化；筛选/局部范围仍须有快速准确算法，不能只缓存默认图。
- 利用整数计数、静态plan的前缀计数和分层区间汇总；必要时加原生查询helper。中间结构按批次跨Python边界，最后才生成页面JSON。

实现形式不强制：可以兼容新增索引文件/块或升级格式版本，并保留旧记录读路径。不要求推倒已有store，也不要求第一步就建复杂通用数据库。

### 4.2 导航

- instruction前/后一步使用指令区间/稀有事件位置直接定位。短期也可从目标之前最近的检查点进行**有界**重放，不能从整个序列块头部扫描。
- call/return/exception/issue继续使用已有稀疏NAV。
- PC/源码导航使用静态ID与动态出现位置/plan位置索引；不能每次从头扫描19M事件。不存在目标、末端回绕和搜索无命中的情况也要测。
- 当前导航只需恢复返回事件及必要历史状态；不要为了寻找序号先恢复全部路径。

### 4.3 不能破坏的窗口语义

精确区间首尾、周期只计归属指令、未知/未成立状态、首事件/首指令、call进入窗口的前驱关系、IRQ pending状态、mixed/common-prefix路径、marker顺序、隐藏未成立和搜索口径全部与现有参考一致。

聚合不是简单相加所有列：调用次数/IRQ等需要首尾边界状态。先在字段规范中定义合并规则，再用跨调用/异常/检查点的窗口验证。

### 4.4 R1验收门槛

- 现有合成规模store：首次**冷**全段window和timeline分别≤1秒；至少50个固定种子局部/跨块窗口做字段对照及计时。
- 导航覆盖正反向/稀疏命中/无命中/回绕，P95≤200ms；首次和重复分开记录。
- 首中末页、搜索、隐藏未成立、event、源码、包视图保持可用；真实浏览器加载不再被慢图挡住。
- 做结构性检查：普通大窗口不得出现与逻辑指令数同量级的Python event字典构造/`CallTracker.feed_instruction()`；只看热缓存不算通过。
- 一次性生成新查询索引的时间和体积要记录；最终纳入新输入处理计时，不能把数分钟成本移到首个查询之外后宣称整体达标。

## 5. R2：实现真正原生的完整 store builder

### 5.1 取消这一条主路线

不要把下一轮主要成果限定成“只把CallTracker换成常驻C++，Python仍解析每条native记录并组装区间”。也不要继续尝试纯Python FastCallTracker作为主路线。

DS自己的profile：tracker约11秒，剩余Python记录/区间处理约19秒。即使tracker降到0秒，200ms也远达不到≤3秒。只替换tracker是可选局部里程碑，不能作为完成交付。

### 5.2 原生边界

新增例如 `etm_storebuild`，一次调用完成：

```text
native.bin + 静态指令/源码字典 + 参数
  → 原生记录解析
  → range计划、末指令/谓词/周期状态
  → 调用/IRQ/返回状态
  → 动态区间、检查点、导航、查询聚合
  → 完整store + 统计 + 原子发布所需元数据
```

Python可以保留一次性的ELF/DWARF/静态指令准备与服务管理，但不能为每条动态指令/元素进行一次函数调用、IPC往返或JSON序列化。

可先让C++预扫描native流导出唯一地址范围/所需指令集合，Python只对唯一集合准备字典，再交C++构建。该额外顺序扫描需计时，但避免了为迁移热循环先重写整套DWARF解析器。若唯一集合过大，采用有界批次，不能退回逐动态事件跨语言通信。

第一版允许读native.bin文件；验证通过后再考虑把OpenCSD回调与writer融合、减少中间写入。**不要把正确性风险大的“整套融合一步到位”作为最小原生版本的前提。**

### 5.3 解除错误的字节布局约束

原P3b报告说“原生产出必须与现有store逐字节一致，所以必须让Python同步请求检查点”，这个结论不成立。

必须保持的是格式规范、逻辑事件/查询、未知/周期/质量语义和旧记录兼容。generation、字符串ID分配、合法检查点布局和压缩块组织不需要与Python参考逐字节相同。可以采用兼容新块或明确新版本，并以规范化逐事件/逐接口结果证明等价。

物理ETM/TPIU和承诺兼容的旧文本导出仍按相应要求对照。保留现有字节一致测试作为辅助，不让内部编码顺序绑住原生架构。

### 5.4 R2验收门槛

- 两份真实200ms以及ETMv3/4小样本，完整逐事件、质量、analysis和查询对照无未解释差异。
- checkpoint×谓词未知的已修缺陷最小用例与100×压力输入保持通过。
- **含输入核验、必要统计/索引/默认轨迹、完整发布**：`etm.bin → 可查询store` 200ms目标≤1.5秒，争取≤1.2秒；合成规模目标≤4秒。均为工程门槛，未达到则交真实profile继续修，不能写成已达到。
- 不带profiler交错至少3次，结果列全部样本；Python动态事件工作量须由profile证明已退出主热循环。
- 加入R1查询信息后重测体积、RSS与写入时间，不使用一个缺索引的极简writer冒充最终writer。

## 6. R3：把原生前端接入实验全链路，控制整体预算
