## 下次复测沿用的做法

1. **先确认芯片身份和初态。** H743 的 AP2 能先读到芯片 ID。遇到 AP0 核心检查失败，先在同一 DAP 的 AP2 开启并读回 DBGMCU 调试时钟，再检查 CPUID。ARM JTAG 用实际 TAP 链核对连接。保留实际加载的官方 CFG、复位前的 VTOR／MPU 状态和请求档，物理 TCK 以外部测量为准。
2. **把探测、写入和回读分开。** HPM6800EVK 运行 XIP 时，OpenOCD 的 `flash probe` 会调用目标端 ROM 算法重新配置 XPI，随后恢复运行可复现 RTT 停流和 hart 无法暂停。独立校验直接读映射区。写入前双读备份，结束后分别确认恢复范围的字节、目标业务心跳和探针所有权。
3. **RTT 用递增序号对账。** 同板、同探针、同 ELF、同环大小和搬运块，用独立的稳态窗测速。STOP 后等 CDC 尾部交付，核对原始字节、探针 `moved` 和目标 `RdOff`。固定重复文本适合查错位，递增序号还能查出整条记录的缺失和重复。
4. **J-Scope 分别记录调度、USB 和收尾。** 以探针时基计算实际采样率和调度跳拍，分别记录 USB 缓冲丢样、读取错误和包序缺口。独立解析 DEF、DATA 和载荷长度，并与 STOP 后 `produced` 对账。HPM EP `0x83` 保持最后 DATA、ZLP 和 action 13 的退役顺序。八路 762 tick 曾有 Web USB 丢样，764 tick 是双方共同验证的稳定档。
5. **保留真正的客户端和发布身份。** 工作台 CLI 驱动网页时，注明它使用同一浏览器后端。原生 CLI 记录实际 USB 路径和计时边界。跨页交接后做一次真实只读访问确认链路，再开始写入或采集。发布时分别记录源码提交、探针 APP、冻结 EXE 和线上构建时间，完整下载 ZIP 核对大小与 SHA-256。 [原生链路恢复复核](zynq-hazard3-cli-recovery-20261110.md) · [正式 web.21](https://github.com/minichao9901/superlinkPRO/releases/tag/workbench-v1.1.0-web.21)

## 保留的复测项

- H743 的 SDRAM 运行且 MPU 开启初态（ISSUE-137）、SWO 实际收数和起点清理（ISSUE-144）、10 MHz SWD 的 Scope 夹具首轮单步（ISSUE-145）。ETM 实板识别已通过，新波形需要 KingstVIS 和采集接线。web.21 未在 H743 上重跑完整矩阵。
- HPM6800EVK 的 JTAG 座未接目标 NRST，软件复位已验证。外接总线和真实 UART 回环仍需对应接线。极端浏览器阻塞或更快周期仍可能耗尽 USB 预读与探针缓冲。
- 首次浏览器选设备、物理冷启后的双探针权限复用，以及 Chrome 回环访问被拒时的提示，继续按 ISSUE-141、146 跟踪。 [问题跟踪表](../项目问题跟踪列表.md)
