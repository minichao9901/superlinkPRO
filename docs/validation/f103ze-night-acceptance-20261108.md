### 软件复位请求与向量捕获对照

原 48 MHz 固件，SWD 1 MHz。每组先由 NRST 建立起始状态，再以 RMVF 清除 `RCC_CSR` 复位标志并读回。Flash 和启动别名的向量一致，预期 PC `0x08000248`、MSP `0x20010000`。停机寄存器通过 DCRSR/DCRDR 直接读回。对照前确认 DEMCR 向量捕获位能置位，AIRCR 的 PRIGROUP 可用同一写钥匙写入并读回。 [ST RM0008](https://www.st.com/resource/en/reference_manual/cd00171190-stm32f101-103-105-107-stm32f100-series-armbased-32bit-mcus-stmicroelectronics.pdf) · [ST PM0056](https://www.st.com/resource/en/programming_manual/pm0056-stm32f10xxx20xxx21xxxl1xxxx-cortex-m3-programming-manual-stmicroelectronics.pdf)

| 对照 | 实测证据 | 判定 |
| --- | --- | --- |
| OpenOCD `reset run` | 日志到达 SYSRESETREQ，命令返回，RCC_CSR 清零后仍为 `0x0`，时钟不变 | 未观察到系统复位 |
| MEM-AP 写 SYSRESETREQ | 停机、运行态及保留原 PRIGROUP 的对照均未置 `SFTRSTF`。停机对照 PC、MSP 不变 | 未观察到系统复位 |
| CPU 执行 SYSRESETREQ | 临时 SRAM 指令执行到 `0x2000f00c` 等待环，R0/R1 分别为 `0xe000ed0c` 和 `0x05fa0004`。保持和关闭 `C_DEBUGEN` 两种条件均复现，RCC_CSR 为 `0x0` | CPU 发出的系统复位请求也未生效 |
| MEM-AP 写 VECTRESET | `DHCSR=0x02030003`、`DFSR=0x8`，PC/MSP 命中启动向量。RCC 时钟保留，RCC_CSR 为 `0x0` | 核复位与捕获通过 |
| 真实 NRST 后向量捕获 | 回读探针引脚拉低并释放。RCC_CSR `0x04000000`、RCC CFGR `0x0`、`DFSR=0x8`，PC/MSP 命中启动向量 | 板级复位与捕获通过 |

CPU 对照使用 24 B SRAM，执行后在停机状态逐字节还原。当前板的系统复位请求未产生可见复位，芯片集成或板级原因还需其他样品对照。ST 高容量 F103 勘误未列该 SYSRESETREQ 现象。F02.03 和 F02.04 保持未通过，VECTRESET 与 NRST 分开记录。 [ST ES0340](https://www.st.com/resource/en/errata_sheet/es0340-stm32f101xcde-stm32f103xcde-device-errata-stmicroelectronics.pdf)

Wasm 旧运行时的无 USB `ms` 命令间隔 90 ms 仍读 `-1 → -1`。上游优先选了 Emscripten 头文件定义但 WASI 接口不支持的 `CLOCK_MONOTONIC_RAW`，导致 `target_wait_state` 的 1 秒截止条件无法推进。浏览器链接改用 Emscripten 的单调时间，`ms` 对照为 `80 → 183`，推进 103 ms。专项回归在旧运行时失败，新运行时 25 项目标、Flash 和 Web 回归通过。 [构建入口](../../web/tools/dev/link-openocd-core-wasm.py) · [Wasm 时钟适配](../../web/tools/dev/openocd-browser-loop.c)

新 Wasm SHA-256 `2424ca855f49ad428896d39c5774f4e1abb665cb3f6a8e69753bc6a79b3a4ec6` 已同步源码运行时。8878 Chrome 从提交 `resetHalt` 到错误回传为 1,138 ms，返回 `TARGET: workbench.cpu - Not halted`。命令后原 DEMCR 值可读且一致，RCC_CSR 仍为零，SWD 能继续读寄存器并正常释放。另用同一 Wasm 与 Node WebUSB 设 `reset_config srst_only srst_nogate`，`reset halt` 在约 79 ms 内以 `PINRSTF`、正确 PC/MSP 和停机状态通过。这项使用真实 NRST，作为板级复位对照登记。冻结包待复验。 [ISSUE-125](../项目问题跟踪列表.md)

### 60 MHz 块读偶发错误定位

交错测试 40 次，每次从 1 MHz 经过已校验的阶梯档到 45 MHz，再到 60 MHz。一半在 45 MHz 先做一次经过对账的 20 KiB 读，另一半只做档位和 PPB 检查。40 次 60 MHz 的 DHCSR 检查全通过，随后的块读两组均为 19／20，通过时全部逐字节一致。两次失败报告的 TAR 分别为 `0x20000bf4`、`0x20000c00`。

增加 WebUSB 回包头采样后再做 96 次，四组各 24 次。每次都在停机状态，按 1 MHz 参考镜像对账。直接调用阶梯设档到 45 MHz、直接调用阶梯设档到 60 MHz、在 45 MHz 验 PPB 后再单独提交 60 MHz，各组均 24／24。45 MHz 先读完整块再单独提交 60 MHz 为 23／24。失败时三次 DHCSR 均为 `0x00030003`，USB IN 返回 `status=ok`，CMSIS-DAP 响应头 `05 05 08`，响应码位 3 为 SWD 协议校验位错误。其余已排队的三个读块仍返回 ACK OK，OpenOCD 重读 DPIDR 成功，随后查到 TAR `0x20000bfc`。TAR 是失败后回读的进度，具体出错位仍须对齐 SWCLK/SWDIO。全程无 SRAM 写入，测试后恢复 1 MHz 并确认 CPU 运行。 [ISSUE-116](../项目问题跟踪列表.md)

固定档对照按 45／60／60／45 MHz 建立四个独立会话，每会话只设档一次，然后连续读 40 次。两档均为 80／80 通过。现有证据将问题缩小到含重新设档的测试场景。40 次和 96 次两组中都曾复现，前者无负载也能触发。短 PPB 通过可用于建链检查，块传输稳定性需独立判定。

临时测量服务退出前确认调试器已断开、目标 CPU 运行，COM34 回复 PONG。13 项会话和传输软件回归通过，Web 合并文件一致性检查通过。两处本轮独占的临时目录共 6,549 个目录项、约 500.2 MB 已移入回收站。正式基线与长期输入保留。

### 50 MHz 接收相位与真机复验

**复核结论。** 本节回报 50 MHz 的旧候选后来证实实际核心时钟约为 12 MHz。相位、SRAM 和 RTT 记录保留为低速诊断证据。真实 50 MHz 实例仍未通过。

原探针先在 1 MHz 做 DPIDR、APIDR、芯片 ID 与 DHCSR 对照。直切 45 MHz、50 MHz 请求档、60 MHz 各六轮，第一条 DP 读全部失败。改用 10→20→36→45 MHz 阶梯后，原固件 45 MHz 和共用其时序的 50 MHz 请求档均六轮正确。60 MHz 的回包均为 ACK OK，但有 5／6 次 DPIDR 为 `0x1ba01277`，1 MHz 真值为 `0x1ba01477`。两值异或为 `0x600`，该模式有两个错位，因此可通过单比特校验。APIDR、芯片 ID 与 DHCSR 仍一致。此现象与之前抓到的 60 MHz 块读校验位错误一起跟踪。

50 MHz 请求用同一探针试了逐命令切频、上电选择 300 MHz 配置、以及在健康 45 MHz 链路升档后保持该 CPU 配置。上电选择候选在 20 MHz 请求档就失败。能从健康 45 MHz 开始的两个对照中，首个 50 MHz 请求档 DPIDR 回 ACK `0x06`，各 6／6 次一致。反复切换 CPU 时钟并非该 ACK 错误的必要条件。

临时诊断引擎在已知 DPIDR 请求后保留探针 FGPIO 看到的 31 个输入采样位。每个相位 6 次一致。50 MHz 请求档的低相位比高相位晚一位，高相位两个取样点均读到完整对齐的 ACK 和随后 28 个 DPIDR 位。原 60 MHz 在三个相位都观察到两位输入延迟。在掉到低速的配置下，重用 60 MHz 引擎会把后续数据位误当成 ACK。试验引擎在当前位高相位采样，数据段每位六个核心周期。
