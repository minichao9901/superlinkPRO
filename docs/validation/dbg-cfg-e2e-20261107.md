# STM32 选型与通用 CFG 的 Web 端到端验收

2026-11-07（北京时间）。源码基线 `ee00aa3cce6ba02cdba4e12a360eba2dc0d34b3c` 加本次工作区改动。使用 Chrome 156 打开 localhost 调试页，真机与模拟结果分别记录。

| 路径 | 验收结果 |
|---|---|
| STM32 内置预设 | 页面显示 19 个 STM32 预设。导入 Nordic CFG 后可切回 H7，手动时钟恢复显示，已导入 CFG 留在下拉中 |
| STM32F103ZE 真机 | 选择内置 STM32F1 及导入官方 `stm32f1x.cfg` 各跑一轮，均在 `main` 停住，源码高亮 20 → 21 → 22，变量 0 → 41 → 42。每轮全量 Flash SHA-256 一致，结束后恢复原固件运行 |
| 非 STM32 官方 CFG | Nordic `nrf52.cfg`、`nordic_nrf52_dk.cfg` 及 GD32 `gd32vf103.cfg` 实际上传、解析和选择对应后端通过 |
| 通用 RV32 协议模拟 | 文件上传 → JTAG 连接 → SBA 写入 12 字节 RAM ELF → 设置 PC 至 `main` → 两次 F10。真实页面显示源码高亮 7 → 9 → 11，模拟寄存器 `a0` 为 0 → 1 → 2。1.5 MHz、6 位 IR、hart 2 从 CFG 传至连接层；DTMCS 的 6 位地址使 DMI 扫描为 40 位。模拟 Flash 全量未变 |

RV32 验收保留生产页面、CMSIS-DAP 封包、TAP 序列、DMI 和 SBA，只替换 USB/HID 端点及目标执行模型。首轮发现设置 PC 后源码视图仍用旧地址，以及切换目标后会自动读取上一块板子的内存窗口。修复后复测，最终脚本每轮打开新文档并验证高亮正文。nRF52832 已有芯片识别及 SRAM 容量校验的软件覆盖，Nordic 与 RV32 真机验收待补。 [机器证据](dbg-cfg-e2e-20261107.json) · [Nordic FICR](https://docs.nordicsemi.com/r/bundle/ps_nrf52832/page/ficr.html)

## 复现浏览器模拟

使用与真机隔离的 Chrome 配置文件，在 CDP 9333 启动 Chrome。本地工作台监听 `127.0.0.1:8899`，浏览器配置中不授予任何 USB 设备。下载固定版本的配置并构建测试 ELF。

```powershell
$out = 'tmp/dbg-cfg-FRESH'
$fixture = 'web/tools/selftest/fixtures/dbg-cfg'
$upstream = 'https://raw.githubusercontent.com/openocd-org/openocd/v0.12.0/tcl'
New-Item -ItemType Directory $out
foreach ($file in 'target/nrf52.cfg', 'board/nordic_nrf52_dk.cfg', 'target/gd32vf103.cfg') {
  Invoke-WebRequest "$upstream/$file" -OutFile "$out/$(Split-Path -Leaf $file)"
}
clang --target=riscv32-none-elf -march=rv32im -mabi=ilp32 -gdwarf-4 -nostdlib -fuse-ld=lld `
  "-Wl,-T,$fixture/rv_ram.ld" '-Wl,--nmagic' "$fixture/rv_ram.S" -o "$out/rv_ram.elf"
node web/tools/selftest/dbg-cfg-page.test.mjs $out
```

F103ZE 的复现步骤见 [RAM 真机验收](ram-debug-f103ze-20261107/README.md) 与 [STM32F1 CFG 真机验收](openocd-f1-cfg-20261107.md)。
