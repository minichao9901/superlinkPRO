# F103ZE Web ETM 联动验收

日期：2026-10-13。共同基线：8460790，工作分支：codex/f103-target。

## 用户操作顺序

1. 载入与目标完全匹配的 ELF，可选择源码目录。
2. 连接 SWD 探针。自动识别高容量 F103 / ETMv3，板上实际 HSE 填 8 MHz。
3. 从 ELF 的函数前“＋”或 `b 文件:行号` 添加断点，圆点选择采集起点。
   本例选 `trace_workload_round`；起点应在时钟/业务外设初始化之后。
4. 在时钟页回读 RCC。本例 CPU/HCLK=48 MHz，Trace 输入=48 MHz，引脚 TRACECLK=24 MHz。
5. 在采集页设 Trace ID=2、Kingst 500 MSa/s、2.0 V、2 ms、通道 0,1,2,3,4、半周期采样位置 0.25。
6. 保持 SWD 联动和自动解码，点击“联动采集”。默认先复位并运行到起点；取消“先复位”则运行至下一次起点。
7. 页面校验 ELF→暂停本页断点→停在起点→配置并回读 ETM/TPIU→武装 Kingst→继续 CPU→保存→解码→恢复本页断点和原设置。

操作结束后可查看执行流、源码、Timeline、调用统计和火焰图。
采集起点的 PC 是明确的断点地址，但首次可信指令仍以 ETM A-Sync/I-Sync 后的解码结果为准；未同步开头不补造路径。

## 固件与 Web 职责

| 内容 | 固件 | Web |
|---|---|---|
| HSE、PLL、CPU/HCLK、Flash 等待周期、业务外设 | 必须正确初始化 | 只读 RCC 并计算，不改应用时钟 |
| 板上晶振频率 | 按真实电路配置 | 用户填写，不能从芯片型号猜 |
| PE2～PE6 | 可提前初始化，运行时不能占用或覆盖 | 打开 GPIOE 并配置 50 MHz 复用推挽、回读 |
| ETM/TPIU/DBGMCU/ITM 同步 | Web 模式不用自行开启 | 配置、回读、停止与恢复 |
| 稳定业务起点 | 提供初始化后可到达的函数/源码位置 | ELF 解析、硬件断点、复位/运行/暂停 |
| LA/解码/存储/导出 | 不需要日志配合 | 浏览器控制与本地服务执行 |

本轮普通固件为 `firmware/stm32f103_cdc_trace/fw-ze-48-workload.elf`，不使用 `-StandaloneEtm`。
构建：`build.ps1 -Chip ze -CpuMHz 48 -TraceWorkload`。原独立 Trace 档仍保留，用于直接 LA 采样。

F103 的 ETM-M3 没有 H7 的 Funnel/ETF；只访问自身 ETM/TPIU 寄存器。
返回栈压缩和周期准确模式在此 ETM-M3 中属于保留位，页面禁用，驱动对请求 true 明确拒绝。
F103恢复原 ETM/同步/GPIO 设置时，TPIU 的 SPPR 始终保持并行模式 0；不在会话内改回 SWO 1/2，避免已知动态切换停钟。
因此“恢复”不等于把 TPIU 切回 SWO；切换其他 Trace 协议前应重新复位目标，并由相应页面配置。

## 实板证据

运行的是实际 `web/app/target.js` / `target-f103.js` 与实际 Flask 采集 API。
为避免慢速桌面操作，验收脚本通过一个持续 SWD 会话给网页控制器提供内存读写传输；没有另外重写一套目标寄存器流程。
浏览器 WebUSB 的 USB 授权弹窗没有在该自动验收中操作；目标寄存器、断点、复位、Kingst 和解码链路均是真实设备。

真实三轮：默认复位到断点、无复位运行到断点、再次复位到断点。
每轮恢复约 51,550 条指令记录，2 次 SysTick，包问题/overflow=0，全部映射到源码。
首轮额外验证 127 个完整 round 的八次交替调用和 1～8 次 mix 循环，11,892 次直接分支落点及 37,094 次线性衔接均符合机器码。

错误 ELF 被拒绝；等待未到达断点时取消，临时 FPB 槽位清理且 CPU 保持暂停；CPU 不继续时停止已武装的 LA，任务完成原始保存。
详见 `docs/validation/f103-web-flow.json`。
