# Trace 完整性、准确性与功能差距审计

2026-10-11。当前阶段继续完善独立初版，暂不接入主工具。本次只审计与修正文档/注释，不改采集和解码行为。

后续已落实第一轮改进：完整性视图、IT 未知状态、函数调用计数、计数火焰图和源码热点，详见 [执行流分析第二版](执行流分析第二版.md)。以下为原审计记录，所列“默认已执行”问题已改为保守未知标记，不表示条件结果已能恢复。

## 结论

当前实现是**有限采集窗口内、没有地址范围过滤的指令控制流追踪**。已验证例程在同步、代码镜像匹配的区间内，分支路径、函数交替调用和 SysTick 进入/返回一致。

这不等于从复位开始的完整历史，也不等于任意程序的每条条件指令执行状态均精确恢复。之前“完整 ETMv4 解码”的表述应限定为当前 H7B0 模式；OpenCSD 的完整解码 API 名称不代表所有 ETMv4 可选特性都已支持。

## “全量 trace”的三个含义

1. **没有按函数/地址过滤**：是。ViewInst 恒真，start/stop 比较器未配置；当前例程也没有 privilege 过滤。
2. **指令控制流连续记录，而非 PC 抽样**：是。ETM 输出压缩控制流，解码器结合机器码展开指令路径。
3. **从复位开始、整个运行过程、无遗漏地记录所有执行细节**：不是。LA 目前是有限窗口采集；固件启动一段时间后才打开 ETM；窗口头尾、同步前数据均不完整；H7B0 当前是 instruction-only trace，不能从它还原所有变量或内存值。

完整历史不能靠把采样率或页面表格上限提高来补齐。长期流式能力还取决于 LA 的硬件/接口；当前采用“采满窗口 → 导出 CSV/KVData → 解码”。只有 8 MHz CPU / 约 4 MHz TRACECLK 的实测结论，尚不能推广到满主频。

## 精确性的重要缺口：非分支条件指令

实际 CONFIGR 为 1，其中 bit0 是 **RES1**，不是 INSTP0 的值。COND[10:8] 为 0，表示非分支条件指令追踪关闭。

Arm ETM-M7 支持单独配置条件指令追踪，但使用中的 OpenCSD 1.8.3 完整指令解码器在启用该功能时明确返回不支持。
依据：[Arm ETM-M7 TRM](https://documentation-service.arm.com/static/5e906dfe8259fe2368e2ac54)、[OpenCSD 1.8.3 配置检查](https://github.com/Linaro/OpenCSD/blob/v1.8.3/decoder/source/etmv4/trc_pkt_decode_etmv4i.cpp#L241)。

例如：

```asm
cmp r0, #0
it  eq
moveq r1, #1
```

在当前追踪模式下，仅凭压缩控制流和 ELF，不一定能判断 `moveq` 是否真正生效。`tools/decode_trace.py` 目前把范围内除末条之外的指令默认设为 `executed=True`，这对一般直线指令可以使用，但对 IT 条件指令缺少可靠性标记。

现有实测例程的已恢复指令中没有 IT 块，因此本次分支/函数验收不受这一缺口影响；但不能据此称为通用“逐指令执行状态完全准确”。下一版应区分**路径可知、执行状态可知、执行状态未知**，不能把未知默认当作已执行。

此外，源码执行流是 DWARF 映射后的有序源码片段。一行可能对应多条指令，优化/内联可能改变映射关系，它不是原始 C 语句的唯一逐句执行记录。

## 参考 J-Trace PRO + Ozone 的主要差距

| 能力 | 当前初版 | 差距 |
|---|---|---|
| 长期流式采集与分析 | 短窗口，导出后解码 | 未验证 LA 连续流接口、持续带宽和后台增量解码 |
| 历史指令导航 | 有分页、搜索、源码定位 | 缺历史前后步进、调用/返回导航、故障前回溯视图 |
| 调用栈/中断可视化 | 有函数归属与异常事件 | 未重建调用栈、递归、尾调用、中断嵌套及调用图 |
| 覆盖率 | 已有 PC 与条件分支结果 | 缺指令/基本块/分支/函数/文件覆盖；当前映射率不是覆盖率 |
| 性能分析 | 按函数统计指令记录 | 缺调用次数、累计/自身耗时、耗时分布；指令占比不是 CPU 时间占比 |
| 时间线 | 默认执行顺序；可采周期计数包 | 未将周期计数建立为带边界的时间关系，不具备逐指令精确时间轴 |
| 触发、起止与范围控制 | 定时窗口和 D0 边沿触发 | 缺代码位置起止、故障/断点触发和前后窗口；硬件能力需按 H7B0 资源核对 |
| RTOS 与其他数据关联 | 无 | 缺任务切换/任务归属，以及变量、RTT/ITM/外设或功耗的关联 |
| 采集质量与完整性报告 | 原始文件和部分诊断保留 | 缺逐层字节核算、区段可信度、所有错误/溢出日志与复杂程序验收 |

对标依据：[SEGGER 功能总览](https://www.segger.com/products/development-tools/ozone-j-link-debugger/technology/trace-features/)、[覆盖率](https://www.segger.com/products/development-tools/ozone-j-link-debugger/technology/code-coverage/)、[系统与性能分析](https://www.segger.com/products/development-tools/ozone-j-link-debugger/technology/system-and-performance-analysis-tracing-and-profiling/)、[起止点](https://kb.segger.com/Trace_Start_Stop_Points)、[J-Trace 功能](https://kb.segger.com/J-Trace)。具体功能受目标资源和探针型号约束。

J-Trace 也会遇到目标输出带宽、主机处理速度和信号质量导致的溢出或未知包，不能把专业探针当作无条件无损保证：[SEGGER 溢出说明](https://kb.segger.com/J-Trace_overflow_error)。

## 建议的下一轮

优先完善可信度，再增加分析视图：

1. **完整性报告与执行状态语义**：逐层字节核算；显示未同步/未知源/尾部/溢出/错误区段；将未证实的条件执行状态标为未知；区分源码映射率与覆盖率。
2. **扩大准确性验收**：IT 块、函数指针、间接返回、尾调用、嵌套中断、异常返回、HardFault 与优化/内联，以及损坏/截断输入；用独立预期路径验证。
3. **调用树、中断层级和覆盖率**：建立在可信区段上；采集开始于函数中途时保留未知祖先，跨缺口不连接调用栈。
4. 之后再做时间分析与长期采集，根据实际周期信息和 LA 接口能力决定实现范围。
