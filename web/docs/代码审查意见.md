## 一、实锤 bug（已脚本复现）

### 1. `_withLock` 的“可重入”快路径会放行外部并发调用，互斥完全失效
`app/rtt/dap-webusb.js:724`

```js
async _withLock(fn){
  if (this._locked){ return await fn(); }   // 分不清"内部重入"还是"外部并发"
  ...
}
```

锁被持有时（A 在 `fn` 内 await USB 期间），**任何外部调用**（用户下行发送 `writeDown`、复位、看门狗 `run()`）都会命中 `this._locked === true` 而直接执行——TAR、AP 挂起读流水线、posted 写这些共享状态照样被交错，正是 `app/rtt/dap-webusb.js:713` 注释里描述的“命令写丢（页面发送成功、固件一个字节都没收到）”那一类故障。复现：A 持锁挂起时调 B，执行顺序为 `A-start, B-start, B-end, A-end`。

修法：去掉重入快路径，内部需要嵌套的地方（`_writeMemLocked` 里的回读、非对齐读-改-写）直接调 `_readMemLocked/_writeMemLocked` 私有函数，让 `_withLock` 只服务外部入口（`readMem/writeMem`）。

### 2. `AkaLinkHid.xfer` 超时定时器成功后不清理，会把在飞的新请求“无声挂死”
`app/hid/probe.js:263-269`

```js
const wait = new Promise((resolve, reject) => {
  this._pending = { cmd, resolve, reject };
  setTimeout(() => {
    if (this._pending && this._pending.cmd === cmd){ this._pending = null; reject(...); }
  }, timeout);
});
```

两个缺陷叠加：① 响应到达后 `setTimeout` 没有清除；② 回调按 `cmd`（0x31/0x32）匹配而不是按请求身份匹配。后果比“误报超时”更糟：早先请求的残雷触发时，`reject` 落在早已 settle 的旧 promise 上（无效），但 `this._pending = null` 会**注销当前在飞的请求**——它既不 resolve 也不 reject，**永久挂起**，迟到的真回包也因 `_pending` 为空被丢弃。复现：请求①（timeout=100ms）10ms 内正常回包；30ms 时发请求②（timeout=5s，250ms 才回）；100ms 时①的残雷把②杀掉，②永远不返回。

影响面：RTT 转发页每 2s 轮询 `status()`、J-Scope 启动时每 120ms 轮询——都是同命令高频请求，撞上一次就是“点按钮没反应、也没有报错”，只能刷新页面。修法：保存 timer id 并在响应路径 `clearTimeout`；`_pending` 里带自增序号，超时回调按序号匹配。

### 3. DWARF 解析器调用了不存在的方法：`r.skip(8)`
`app/elf/dwarf.js:246` —— `case FORM.ref_sig8: r.skip(8);`，但 `R` 类（第 98-110 行）只有 `u8/u16/u32/u64/uleb/sleb/bytes`，没有 `skip`。遇到 `DW_FORM_ref_sig8`（DWARF4 的 type units，如 GCC `-fdebug-types-section`）会直接 `TypeError: r.skip is not a function`，把一个“支持的 form”变成解析崩溃。改成 `r.bytes(8)` 即可。

## 二、逻辑 bug（代码证据确凿，未起硬件复现）

4. **RTT 上行“错位读重试”在环形绕回时会读越界**（`app/rtt/protocol.js:210-216`）：正常路径绕回时分两段读，但 corrupt 重试是单段 `readMem(e.pbuf + e.rd, n)` —— 跨过缓冲末端读相邻内存。只要重试数据里恰好没有 "SEGGER RTT" 签名，`data = retry` 就把**未绕回的错误数据**当正常数据用掉并推进 RdOff（静默数据损坏）。重试必须按同样的两段逻辑重组。

5. **串口写队列会被一次失败“毒化”**（`app/serial/session.js:103-109`）：`this._wq = this._wq.then(...).catch(e => { emit; throw e; })` 把链留在 rejected 状态，之后所有 `write()` 的执行体都被跳过、重复上报**旧**错误，直到重开串口。catch 里不应 rethrow（错误已走 'error' 事件）。

6. **ANSI 模式下“高速期间省略了 X 的渲染”提示永远不显示**：`app/serial/assistant.js:361-377` 和 `app/hid/stream.js:206-222` 都是先调 `this.rx.setDisplayOff(false)`（RxBuffer 内部已把 `suppressedBytes` 清零）再读 `this.rx.suppressedBytes` → 恒为 0。`app/rtt/view.js:712` 的同款代码用自己的 `suppBytes` 记账，是对的——照它改即可。

7. **J-Scope 起跑段数据被丢**（`app/scope/view.js:806`）：DATA 分支的 `if (!this.running) break;` 会把 **DEF 已到、START 的 STATUS 轮询（约 120-240ms）尚未 resolve 期间**的新一轮数据整包丢弃。丢弃旧会话残留的职责已由 `_awaitDef` 承担（DEF 就是起跑线），这层额外 gate 只会误伤新数据——起跑 ~0-240ms 的样本丢失、触发也晚布防。建议改成 `if (!this.running && this._awaitDef) break;` 或干脆只依赖 `_awaitDef`。

8. **桥的安全缺口**（`bridge/rtt-bridge.mjs`）：`--token` 被解析但**从未校验**（死参数）；WS upgrade 也不检查 `Origin`。桥只听 127.0.0.1，但浏览器允许任意网页向 `ws://127.0.0.1:17321/ws` 发起跨源 WebSocket（CSWSH）——等于任何打开的网页都能驱动本机 OpenOCD/J-Link 读内存、**烧固件**。加一行 Origin 白名单（或把 token 真正用起来）。

## 三、数据/设计疑点（需要你确认意图）

9. **烧录算法表的 `flash_length` 疑似系统性偏小**（`app/flash/algos.js`）：`stm32f4: 65536`（64KB——最小的 F4 也有 256KB）、`stm32f7: 131072`、`stm32l4: 262144`（L476 是 1MB）……`flash/view.js:366` 的 `_checkRange` 会拒绝合法固件并误导向“芯片选对了吗”。F1 的擦除粒度已经做了按 DEV_ID 动态判定的先例（那次 bug 修得很漂亮），flash_length 建议同样处理，或按系列取上限。

10. **「绝对时间」复选框是无功能摆设**：`app/core/format.js:6-11` `stamp()` 的 `absolute` 参数两个分支完全相同（注释也自认了）。串口助手和 RTT 转发页的 `s-tsabs`/`c-tsabs` 勾了没有任何效果。要么实现“相对页面打开时刻”，要么删控件。

11. **桥的 `rpc()` 无串行化**（`bridge/rtt-bridge.mjs:360-380`）：两个并发 RPC（RTT 轮询 `mem.read` + 用户点复位）共享同一 socket 和 `this.buf`，响应可能错配。`handle()` 不 await、每条消息独立进 handler，窗口真实存在。dap-webusb 那边为同类问题修过整条锁链，桥这边没有防护——OpenOCD 路径速率低，概率小，但值得补。
