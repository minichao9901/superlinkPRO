## 1. 探针 `rc=-4`：60 MHz 换挡瞬态 + 缺一层重试

**现象**：页面 J-Scope 偶尔报「该档位链路不可用」（`rc=-4`），一出现整轮编排前半段白跑。

**定位过程**（工具 `tools/selftest/probe-hid-diag.py`，HID 直驱、绕开页面）：

1. 分档扫描：**60 MHz 档 87/670 ≈ 13% 失败**（单轮 3%~17%），**8/20/45 MHz 0/301**；与采不采样、
   采哪个地址无关。
2. 判定"失败在哪一级"：一次 scope START 在固件里是两级串联 ——
   ① `rtt_swd_init()`（JTAG2SWD + DP 上电 + 20M→目标档 斜坡 + 吃掉瞬态的一次 DP 读）
   ② AP 验收读 `rtt_bridge_read(span[0].start, 4 B)`（`scope_sampler.c:757`）
   用 HID `CMD_RTT` action 5（PEEK）读**探针自己的** `s_swd_ready`
   （`0x81EAD`，符号地址取自 `build_dfu_evklite/output/akaLinkPro_App.map`）：
   **失败 6 次全是 1** ⇒ 初始化成功，挂的是②。旁证：桥的 AUTOSTART 走同一条初始化，100/100 rc=0。
3. "重试能不能救"：BENCH（同一个 `rtt_read_bytes`，自带一次零延迟重试+清 sticky）在失败的那 6 次里
   **同样全失败**；失败后按 0/2/5/10/20/50/100 ms 连探 **18/18 全失败** ⇒ **光重试没用，必须重新初始化**。

**根因**：换挡后第一次 AP 访问会瞬态失败（固件注释里早写着「换挡后的第一次访问最容易踩到瞬态」），
桥的 `rtt_find_cb()` 有"清 sticky + 就地重读一次"+ 外层 3 次重扫，`rtt_bridge_run_bench()` 也有一次重试，
**只有 scope 的验收读一次都不重试**。

**修法**（akaLinkPro `bbb86a8`）：新增导出 `rtt_bridge_link_recover()`（SWD：能降就降一档 + 清 sticky +
**重新初始化**；RISC-V：重开 TAP/DM），`scope_link_try()` 的验收读失败时走它再读一次，恢复成功后把
`s_clock_hz` 同步成实际生效档位。

**验证**：60 MHz × 200 次 START **0 失败**（其中 8 次真的走了恢复路径，状态字如实报 45 MHz）；
45 MHz 及以下本来就 0/301。

## 2. 「P2.rtt@45M 丢 17 字节」：相位假象 + ≤2 KB 重复前缀

**现象**：`make regression-swd` 的 P2 里偶发 `LOSSY/GARBLED：1 gap(s), 17 bytes lost`，`rd_err=wr_err=0`。

**为什么这个数字不能当字节数**：`rtt_probe_bridge.py` 用固定图案 `"hello world!\n"`（13 B）逐条
`find()`，相位断裂能报出来的值只有 **1..24** —— **丢 5 字节和丢 5 MB 报出来是一个量级**。

**真字节级测量**：造了等长（13 B）带序号靶子 `tools/target-firmware/stm32f103_rtt_seq`（`"seq %07u\r\n"`，
其余与 speed 版完全相同：BLOCK_IF_FIFO_FULL + 96 MHz + 32 KB 环），逐条对账：
45/60 MHz 共 8 个窗口 **~262 MB：真丢 0 B、坏记录 0**；唯一的异常是某些窗口**开头 ~2 KB 的记录号回退**
（155/156 条 = 2015/2028 B）= **重复**前缀，不是丢失。固定图案下同一现象就是
`gap=1 lost=5/9/20 first@2036`（位置恒在采集边界），且探针 `drained == 主机收到`（rd_err=0）。

**根因**：`rtt_poll_once()` 里 RdOff 回写失败的兜底是"记 pending、下一轮幂等补写"，但**会话收尾那一笔
没人补**（`rtt_bridge_stop()` / `rtt_bridge_start()` 都把 pending 清掉）；目标侧 RdOff 落后 ≤2 KB，
下一次启动桥就把这段**重读一遍**（安全方向：宁可重读不可丢）。

**修法**（akaLinkPro `bbb86a8`）：HID 的 STOP 与 scope 的 START 改成 `rtt_bridge_request_stop()`
（**排队到主循环**执行 —— USB 中断里不能碰 SWD）；主循环服务时先 `rtt_bridge_flush_pending_rd()`
补写（幂等、最多 4 次 + 清 sticky）；重启前若会话还活着也补一笔；`rtt_bridge_note_dap_activity()`
里把 pending 作废（主机碰过 DAP 后目标可能刚复位/重烧，写旧位置会让采样位置凭空前进 = 真丢数据）。

**验证**：45 MHz × 6 窗口 132 MB **真丢 0 / 跳变 0 / 回退 0 / `wr_err` 0**（改前每会话 1 次 `wr_err`
+ 约 1/3 窗口出现重读前缀）；akaLinkPro `make regression-swd` **PASS fails=0**（P2 20/45/60M =
1389/2512/2977 KB/s 全部 LOSSLESS，吞吐无回归）。

> 顺带两条测量纪律：**HID-only 跑 scope 类模式会把探针包缓冲池耗光**（采样器往 USB 0x83 推包，
> 工具不读 → 之后标定稳定 `err=-5`，测完重烧探针）；**量丢字节必须有后台读线程从会话一开始就排空
> 串口**（驱动 rx 缓冲 4 KB，2.6 MB/s 下 1.6 ms 就满，一边 HID 轮询一边不读 → OS 静默丢字节）。

## 3. HPM6800EVK：`full_flow_6800evk` 首次上板

这一条（`41336a6` / `c2c4583` 于 2026-10-03 加入）在硬件上**从没跑过**（记录里写的是"等你换板子"），
第一次跑暴露 7 个问题。性能本身与基线一致（烧录 2.5 s vs 基线 8.4~10.5 s、Viewer 66~71 KB/s、
转发 1.387~1.388 MB/s、J-Scope 253~256 / 40.6 kHz）。

### 3.1 RTT Viewer（RISC-V/SBA）

| # | 现象 | 根因 | 修法 |
|---|---|---|---|
| 1 | 连上却 0 B/s，状态栏「SBA 读 0x… 出错（sbcs=0x400ca2）」；最坏 `dmstatus` 读出 `0x6c726f77`（ASCII **"worl"**，环里的数据） | 连上后去读 RTT **通道名** `sName`，而它在 **XIP flash**（0x8000cf1c）→ SBA 读那个窗口**永久挂起**，1.2 s 超时后事务仍挂着 → `sbcs.sbbusyerror` 变 sticky，之后每个环读都失败 | `RiscvMem.skipNames` + `protocol.js` 的 `name()` 跳过（名字只是显示用；ARM 那条路照旧读） |
| 2 | 首次连接就要自愈好几秒 | 没有连接期健康检查 | 连接阶段先 `dm.sbaHealthCheck()`（清错 → 复位 DM → 必要时 ndmreset），结果挂 `mem.health`（含 `slow`） |
| 3 | 读到一次错之后**每条**都错 | `dm.init()`（dmcontrol 0→1）**不清** `sbcs`/`abstractcs` 的错误位 | `RiscvMem._read` 的自愈改成**先清 sticky 再复位 DM** |

### 3.2 编排（`tools/selftest/hw-campaign-hpm.mjs`）

| # | 现象 | 根因 | 修法 |
|---|---|---|---|
| 4 | 连上但 `running=false` / 首轮卡死 / 轮询慢到 0.1 Hz | 上一格（读 IDCODE、上一轮 J-Scope 采样）留下的**在飞 USB 传输** | 连接前统一清场（停采样 transport + 断开 RTT 会话 + `probe.recover()`）；"连上没轮询/首轮没跑完"算**连接失败**整轮重连（重连会复位 USB 端口+清队列）；首轮卡住两级升级：清错复位 DM → ndmreset |
| 5 | 转发那一格 CDP `Runtime.evaluate` 直接超时（页面像死了） | flood 环 8 MB、Viewer 那格只有 ~70 KB/s → 到转发时环是满的，桥一起就以 **~6.5 MB/s** 灌 CDC（实测探针侧 6.460 vs 页面 1.392） | 开 CDC 口**之前**用探针的丢弃模式（HID 0x31 action 7 flags bit0）抽干积压（实测抽掉 5.58 MB），之后量的是**稳态** |
| 6 | 后台页面会让短延时被钳到 1 s、写盘降速 | 窗口被遮住 | 前置 `Page.bringToFront` + 打印 visibility/focus |

### 3.3 RISC-V 调试（`#dbg`）

| # | 现象 | 根因 | 修法 |
|---|---|---|---|
| 7a | 编 4 个断点中途失败 → 紧接着读 PC 就 `cmderr=3`，整轮套件中断 | `abstractcs.cmderr` 是**写 1 才清**的 sticky 位，一条失败会毒化之后每一条 | `RiscvTransport._abstractRetry()`：失败 → 清 cmderr（写 0x700）→ 重试一次 |
| 7b | 抽象命令偶发"要先停住目标" | `session.halted` 是缓存，目标可能已被上一格放跑 | `RiscvDebugSession._ensureHalted()`：读/写寄存器前用 `dmstatus` 现核，跑着就先 halt |
| 7c | 跨断点单步后 `cont()` 里读 PC 打空 | RISC-V 单步收尾会放开核，此时核已在跑 | `cont()`：单步后若核已在跑，语义上"继续"已达成 → 直接返回 true |

### 3.4 STM32H743：`full_flow_h743` 首次上板（同一天晚些时候）

H743（阿波罗 H743，IDCODE `0x6BA02477` / DEV_ID `0x450` / 2048 KB）接上后第一次跑
`make full_flow_h743`，**一处潜伏 bug 直接卡住整轮**：

| 现象 | 根因 | 修法 |
|---|---|---|
| 烧狂发固件 ✅、RTT Viewer 443.6 KB/s ✅，紧接着报 **`cdp.json is not a function`**，编排在转发之前中断 | `hw-campaign.mjs` 的 `feedHidElf()`（只在 **`BOARD.findCb === 'elf'`** 时调用 = **只有 H743 走这条路**）写了 `cdp.json(...)`，而这个文件里的内联 `Cdp` 类只有 `evalJson` —— F103 走"自动搜控制块"，**永远进不到这一行**，所以那轮全绿也照不出它 | 改成 `cdp.evalJson(...)`，并给内联类补一个 `json()` 别名（两套 CDP 封装名字不同，留别名免得再踩） |

修完重跑，**`make full_flow_h743` exit 0**：

| 项 | 实测 | spec |
|---|---|---|
| 烧狂发 / scope | 2.4~2.6 s | — |
| RTT Viewer（WebUSB · 60 MHz） | **447.1 / 477.7 KB/s**（轮询 37~40 Hz） | > 300 KB/s |
| RTT 转发（页面 RX） | **2.90 / 2.90 MB/s**（探针侧 2.59 / 2.61） | > 2.5 MB/s |
| 转发 10 s 存盘 | 29.39 / 29.29 MB，一致性 **99.6 / 99.5%** | ≥ 98% |
| 交替烧录 5 遍 | 全部 ~2.5 s | — |
| `test-dbg-stress`（调试压力） | **82 通过 / 0 失败** | 全过 |

调试压力那轮的 gdb 对照：`engine_linear` 内 17 步**逐步一致**（含两次函数调用）、
`文件:行` 断点落点一致、复位向量一致（0x8000880）、位域排布经 gdb 逐字段核对；
步**出**函数之后两边口径不同（调用者被内联时我们按地址序下一条语句、gdb 按行号变化，两者都还在 `main` 里）。

## 4. 判据/口径修正

- **3 变量 @20µs 判零跳拍是超能力请求**：3 变量（1 span / 12 B）的读循环实测 **24.5 µs ≈ 40.8 kHz**
  —— 与基线记录的 40.8 kHz **完全一致**，所以 20 µs 周期必然跳拍（今天丢 26182 拍，但 **USB 丢 0、
  seq 缺口 0**）。基线里的"50 kHz 零丢"指的是 **1 变量**那档（今天 50.00 kHz / 0 跳拍 ✓）。
  → HPM campaign 的 3 变量档改成 **30 µs**（留 ~20% 余量）判零丢；表格行名改成"低速率档丢样本"。
- **`--record` 跑不会因某行不达标而中断**（只打印"实测×80%"的 spec 建议）→ 复查时注意区分
  "绿"是判决跑还是记录跑。
- 固定图案的 `gap/lost` 是**相位**口径，不能当字节数（见 §2）。
