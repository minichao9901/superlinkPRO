# ETM 执行轨迹：更多功能中的本地工作台

菜单：**更多功能 → ETM 执行轨迹**。ETM完整页面内嵌在工具箱内，保留ELF、断点、时钟、采集、执行流、Timeline、火焰图和源码浏览。

需要交接 AI 进行 STM32H7B0 实板测试时，按 [H7B0 操作与实板验收手册](etm-h7b0-operation-and-acceptance.md) 执行：包含稳定固件指纹、接线、实际端口、业务起点、自动化接口、操作顺序矩阵和证据交付要求。

## 启动

推荐从 **工程生成 → ETM 桥** 点击“下载完整 ETM 桥包”。解压整个文件夹，双击 `check-tools.bat` 预检，再双击 `start-etm-bridge.bat`：服务准备就绪后自动打开 ETM 页面。也可用页面的“打开 ETM 工作台”按钮打开已运行的桥。

完整包支持 Windows 64 位，包含 Python、Python 依赖、工具箱/ETM 网页、Kingst 采集分析服务和 OpenCSD 解码器；无需安装 Python、下载两个工程或构建解码器。KingstVIS 及其驱动仍需安装并打开 Socket。包可放在中文或含空格的路径中；端口在 `etm.config.json` 中修改，默认 8878。记录保存在包内 `data/records`，升级前请保留 data。

“仅下载启动文件”提供 BAT、PowerShell、端口配置和说明，适合已有完整包时覆盖同名启动文件。它不包含运行环境；第一次使用请选择完整包。完整包下载时校验 SHA256；仓库中的运行快照、来源清单、许可证和构建方法见 `bridge/etm/README.md`。

ETM的逻辑分析仪采集和OpenCSD解码需要本地服务；串口、RTT、SWO等原有静态网页功能仍可独立使用。

### 开发源码运行（开发者选用）

普通使用无需下面的工具链。本仓把 ETM 页面与后端放在 `etm/` 子树；开发时在 `web/` 目录下运行：

```powershell
python -m pip install -r ../etm/requirements.txt
pwsh -NoProfile -File tools/dev/start-etm.ps1
```

打开 `http://127.0.0.1:8878/#etm`。`etm/` 不在默认位置时，可传 `-EtmRoot '你的ETM子树路径'`；端口可用 `-Port` 调整。本地启动脚本在缺少解码器时调用 `etm/build-decoder.ps1`，需要 CMake/Ninja/MinGW 工具链。已经构建好的解码器会直接复用。

普通静态站点的ETM菜单显示本地启动说明；下载并启动完整桥包，再从本地集成入口打开，即可使用同源内嵌和探针共享。

## 操作顺序

1. 启动KingstVIS并打开其Socket接口（默认23367），使能采集所需的五路通道。
2. 从更多功能进入ETM，载入板上同一份ELF，连接探针；首次使用该地址需在浏览器授权并选择akaLinkPro。
3. 搜索函数，点击前面的＋添加断点，选择圆点作为采集起点。
4. 核对目标与时钟，F103ZE当前验收档为CPU48 MHz、引脚TRACECLK24 MHz；HSE按板卡实际值填写，本板为8 MHz。
5. 配置Kingst：CH0～4=PE2～PE6，共地；本板验收为500 MSa/s、10 ms、2.0 V、相位0.25，分支广播关闭。
6. 点击联动采集，完成后查看执行流、Timeline、火焰图与源码；文件页可保存便携记录。

固件负责CPU/外设时钟和业务程序；网页配置ETM/TPIU及Trace引脚、断点和资源恢复。火焰图宽度表示执行序号或路径记录数，不表示函数耗时。

## 探针共享

内嵌ETM复用主工具的USB驱动、USB租约和ProbeManager。连接ETM时先释放冲突的RTT/调试器/SWO资源；正在采集或控制目标时拒绝其它功能抢占。操作结束后，切到其它功能并连接时会先恢复ETM资源并断开它。普通历史浏览不申请探针。

ETM 原始工程（来源 `web-etm-trace`，`master@12746fc`）已并入本仓 `etm/`；`web/bridge/etm` 保存受审查的运行快照及下载包。完整包不包含 SDK、编译工具链或用户历史记录，只带一个 Demo。独立ETM页面仍能单独启动。PXLogic实验分支未纳入此集成。

## 当前验收

2026-10-14，F103ZE/Kingst同源集成接口验收：复位采集、不复位再次采集、等待时停止、停止后再采集均通过。三次10 ms窗口恢复174786/174785/174786条指令，全部对应源码，overflow、包错误、未处理字节均为0。首次失败记录保留；当时CH4无跳变，用户重新接好后复验通过。

实板使用项目的持续SWD接口运行实际EtmTarget及主工具ProbeManager，再走同源采集/解码接口；不是模拟Trace数据。菜单、内嵌初始化和历史分析在浏览器验收。物理浏览器WebUSB授权/接口转交尚未由自动化完成：测试浏览器启动被自动审批拒绝，现有浏览器的首次USB选择需用户授权。首次在Chrome/Edge打开时请完成设备选择。

### 1.0.2：嵌入页面的复位与调试口恢复

工具箱探针驱动补齐 `writeMemDiagnostic` 和 `recoverDebugPort`。AIRCR 软件复位等控制写只发送一次，不按普通内存的回读差异再次写入；ETM 拒绝缺少该接口的旧驱动。停在非所选起点时，错误提示包含实际 PC 和 DHCSR/DFSR/DEMCR，目标保持暂停供检查。

F103ZE 实板使用生产工具箱探针 JS，经原始 USB 字节转发验收：从 `cdc_acm_init`（0x080004d0）连续三轮复位/Kingst 采集/解码/恢复断点通过，每轮仅一次复位；500 MSa/s、10 ms、1.65 V、分支广播关闭，172581/172601/172581 条指令，overflow 与包错误均为 0。“运行至起点”另以循环函数 `cdc_poll` 验证命中。调试口恢复没有复位或继续 CPU，PC 保持一致。用户原先停在 UART 初始化入口的错误暂停尚未在验收中复现。

`cdc_acm_init` 属于初始化函数，经过后继续运行不会再次调用；再次从它采集应勾选“先复位，再运行至起点”。更新完整桥包时先退出旧桥进程，保留 `data` 目录，再启动新版并刷新页面；只更新网上静态页不会更新已解压桥包中的页面代码。首次浏览器 USB 授权仍须用户完成。

### 1.0.5：H743 实验适配与严格解码

H743 阿波罗板已接入同一工作台：ELF → 硬件断点 → 时钟 → Kingst 联动采集 → 源码/火焰图。板载HSE为25 MHz；本轮验收固件CPU/HCLK60 MHz、物理TRACECLK30 MHz，USB仍为独立PLL3Q48 MHz。完整桥包附H743实验ELF；实际烧录镜像必须与网页载入的ELF一致，网页不会自动烧录或改PLL。

采集页“通道、相位与滤波”增加**解码前软件滤波（ns）**，默认0关闭（**1.0.6 起默认 4 ns**，见下）。当前接线有2 ns窄脉冲，4 ns明确对照通过；原始CSV/KVDAT保留，报告显示处理量。KingstVIS滤波快照不保证CSV导出已应用滤波。该功能不是模拟信号质量修复，也不证明采集全程无丢失。

必须更新完整桥包并重新启动服务。新网页检查captureProtocol=2，拒绝混用旧后台，避免旧解码器忽略滤波参数或继续跨错误帧拼接。只下载BAT/启动脚本不能升级解码器。

长记录使用JSONL和SQLite分页，保留条件执行未知、真实包错误、overflow和捕获边界；CSV取样仍需要与波形规模相关的内存。旧版大JSON需重新解码。当前115项Python、44项源工程Node回归及4次新实板采集通过相应条件；原生浏览器USB授权、物理拔插、其他芯片实板回归和完整初始化至hello连续长窗不在本轮已通过范围。

审查详情、操作步骤和证据索引：[H743 网页复核](h743-web-review-2026-10-17.md)。新源码提交为 `f28299e`，未推送远端。

### 1.0.6：单次采集/解码/页面显示上限 200 ms（不再分窗）

采集、解码与页面显示统一上限 **200 ms**（500 MSa/s 下 1 亿样本，≈478 MB CSV）：一次采集 + 一次解码完成；`/api/capture` 对更长的窗口或更大深度直接 400，页面时长输入上限同步为 200，请求不再带 `sliceSeconds`。同日早些时候的长窗路线（4 s / 21 亿样本 + 后台自动分窗）**当日废止**——1 s 采集的解码实测要 10~30 分钟，不实用；分窗代码只保留给读取/离线重建旧记录（`streamed.schema=3`）。

采集页「通道、相位与滤波」的**解码前软件滤波（ns）默认值由 0 改为 4**：500 MSa/s 下宽度 2 ns 的窄脉冲会把 TPIU 帧对齐切错、使完整解码出包问题；真机 A/B（含 2026-10-18 包地复测）的口径是 **0 ns 不行；2 ns 与 4 ns 已验证**（解出的 ETM 流逐字节相同）；**4 ns 作为默认安全边际**；更大阈值受半周期保护限制，不推广为任意值（包地前的脏会话里 2 ns 仍失败）。原始 CSV/KVDAT 不改写，报告记录处理量；阈值是当前接线/LA 的经验值，不是信号质量改善的证明。

必须更新完整桥包并重启服务（旧后台与新页面的 captureProtocol 校验仍会拒绝混用）。真机证据、根因与局限见 [单次 200 ms 决策与真机验收](../../docs/capture-200ms-2026-10-18.md)。

### 1.0.7：滤波阈值文案改三档（行为与 1.0.6 相同）

只改文案与版本号，不改采集/解码行为：采集页「解码前软件滤波（ns）」的说明改为包地后的三档口径——**0 ns 不行；2/4 ns 已验证（解码结果逐字节相同）；默认 4 ns 是安全边际；更大阈值受半周期保护限制**；同时注明 TRACECLK 包地后已无毛刺，残留的是数据线 D0–D3 的 ≤2 ns 窄脉冲。H743 固件 README 同步该口径。

2026-10-18 包地复测：TRACECLK 毛刺 506 → 0（12,000,307 个时钟跳变 0 事件），TPIU 解复用在 0/2/4 ns 下一致通过；数据线残留 ≤2 ns 跳变使 0 ns 完整解码出现 8 个包问题，2 ns 起为 0。详见 [单次 200 ms 决策与真机验收](../../docs/capture-200ms-2026-10-18.md) §6。

### 1.0.8：解码提速约 7× + 记录包导入/停止语义修复

- **解码提速**：200 ms 记录（500 MB CSV）从 **814–837 s 降到约 119.5 s（≈7×）**。做法是单遍解码流水线（去掉重复序列化/反序列化/多次扫描）、浏览索引 v4（存字节偏移、2.90 GB→1.04 GB、sidecar 指纹判新鲜）、前端 numpy/pandas 向量化取样（可选加速，缺依赖自动回退纯 Python）。产物与改动前逐字节/逐字段一致；`ETM_DECODE_ENGINE=legacy` 可整体回退。便携包**随带** numpy/pandas，包内同样是全速（~120 s）；删除 runtime 里的这两个目录会自动回退纯 Python（约 270 s，结果逐位相同）。详见 [解码提速记录](../../docs/decode-speedup-2026-10-18.md)。
- **记录包可往返**：上传/解压上限改为 1 GiB 上传、1 GiB 单成员、2 GiB 总量，解压改流式落盘——200 ms 单窗的 `.etmrecord`（压缩后约 53 MB）可正常重新导入。
- **停止语义**：单窗路径在导出完成/解码前/解码后三个边界消费停止请求，不再出现“已停止但任务继续跑完”；`/api/stop` 明确提示“当前步骤结束时生效”。
- **滤波文案**：页面与文档统一为“0 ns 不行；2/4 ns 已验证；默认 4 ns 是安全边际；更大阈值受半周期保护限制”。

### 1.0.9：审查 F01–F04 修复（滤波器边界、冻结包加速、索引 sidecar、电平校验）

- **F01（P1）向量滤波器**：修复“首个过窄对出现在索引 0 时把后续合法边沿也删掉”的缺陷（`[0,2,10,22] ns`、阈值 4 原先返回空，应保留 `[10,22]`）；改为按过窄段独立栈模拟，并加 300 组随机边沿与逐条实现的等价比对。**此前用向量化前端解出的记录若时钟首段出现过窄对，可能少边沿；受影响记录应重新解码。**
- **F02（P2）便携包加速**：冻结包此前 `import numpy` 失败（`numpy._core._exceptions` 缺模块）→ 前端静默回退纯 Python。已用 `--collect-all numpy/pandas` 重新打包，并新增不依赖 LA 的 `/api/health`（返回 `frontend.vectorized`）；便携测试会断言加速真的生效。
- **F03（P2）索引 sidecar**：头部升级 v2，记录 `size/行数/mtime_ns/sha256`；events.jsonl 被**等长改写**时旧列不再被复用；v1 头部一律视为过期。升级后首次打开旧记录会重建一次索引（慢一次，之后正常）。
- **F04（P2）电平校验**：通道改按 int16 读入后再校验 0/1；`256/257/-256` 这类越界值不再溢出成 0/1 后通过。

便携包：**1.0.9**，包内 `numpy/pandas` 可正常导入，前端走向量化路径；`--check` 与便携自检 5/5。

### 1.0.10：全记录火焰图不再超时（复用解码统计 + 区间缓存）

- **全记录火焰图**：此前点“火焰图”会对整个区间重扫事件（实测 3.86 M 指令的 `window()` 需 **119.5 s**），前端 45 s 超时 → 图形不出现。现在全记录直接复用解码时算好的 `analysis`，**立即出图**（默认按调用权重）；要看“按执行顺序”的火焰图，先拖选/输入一个执行序号区间（区间越小越快）。
- **区间统计**：`window` 请求超时从 45 s 放宽到 180 s，并显示“正在计算…”提示；服务端对同一区间结果做内存缓存（索引重建时自动清空），第二次打开即时返回。
- 仍建议：大记录上用轨迹图/序号框选局部区间后再看执行顺序火焰图；全记录的时间轴分桶需要遍历全部事件，这一限制没有改变。

### 1.0.12：等待断点超时 15 s → 180 s，且可取消

- **等待函数入口不再逼你手快**：`runTo()` 默认超时从 15 s 放宽到 **180 s**（3 分钟），日志显示“最长 180 秒，可点「取消等待」”；点「联动采集」后可以慢慢打开串口助手再发触发数据。
- **取消等待可用**：采集起点等待期间设置 `state.waiting` 并刷新控件，`#cancel-wait` 会显示；点击即置 `cancelEntry`，`runTo` 循环立即中断并清理一次性断点。
- 状态栏在等待时显示“正在等待所选断点…最长 3 分钟，可点「取消等待」”。
- 说明：`reset()` 的复位路径仍是原有超时；抓 CDC echo 仍建议“联动采集前停在所选断点 + 取消先复位”。

### 1.0.13：KVDAT 直读快链路（首屏约减半，整段窗口约 1 s）

- **采集不再中转 500 MB CSV**：新网页请求 `rawFormat=kvdat`，直接保存 Kingst KVDAT；读取时校验 3.6.x 布局（32 位边沿位置、结束哨兵、未知版本/标志明确拒绝），再走与 CSV 相同的滤波与 DDR 取样。旧客户端未传 `rawFormat` 时仍保存 CSV；旧 CSV/ETM BIN/记录包继续支持。
